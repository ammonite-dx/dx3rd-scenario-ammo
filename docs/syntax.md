# Markdown正本の記法仕様

## 1. 位置付けと適用範囲

本書は、TRPGシナリオを編集するMarkdown正本のMVP記法を定める。前提は
[要件定義書](requirements.md)であり、参照した旧原稿の実例は
[`gift/manuscripts/md4.md`](../gift/manuscripts/md4.md)、
[`gift/manuscripts/cl1.md`](../gift/manuscripts/cl1.md)、
[`gift/manuscripts/md3.md`](../gift/manuscripts/md3.md)、
[`gift/_postReplaceList.json`](../gift/_postReplaceList.json)である。

この仕様が規定する専用ブロックは、次の8種類だけである。

`dialogue`、`roleplay`、`choice`、`check`、`info`、`e-lois`、`battle`、`combo`

本書が規定するのは入力Markdownの文法、属性の型、本文の許可範囲、エラー条件である。Unifiedのノード名、プラグインAPI、利用ライブラリの関数、変換アルゴリズムは規定しない。どの実装でも、同じ入力から同じブロック名・タイトル・属性・本文・位置を得られなければならない。

専用ブロックを表すHTML要素、クラス、`data-*` 属性、ARIA属性、CSSおよび組版上の見た目は、別途 `docs/html-contract.md` で定める。本書の `title` や `{.scene-title}` を、出力HTMLのタグ名やクラス名と同一視してはならない。

## 2. 文書の外枠

### 2.1 章文書の標準形

MVPの章文書は、先頭のYAML frontmatter、通常のH1による章タイトル、その後のMarkdown本文からなる。正本の推奨形は次のとおりである。

```markdown
---
id: MD-04
kicker: ミドルフェイズ・シーン4
lang: ja
---

# Illegal Gifter {.scene-title}

本文または通常のMarkdown。
```

frontmatterは文書の機械可読なメタデータであり、表示上の章タイトルの代用ではない。`kicker` は章タイトルを補足するメタデータであり、H1に置き換えてはならない。`kicker` の表示方法はHTML出力契約の責務である。

### 2.2 frontmatter

- frontmatterはファイルの先頭（任意のUTF-8 BOMを除く）に、単独行の `---` で開始し、次の単独行の `---` で終了する。
- frontmatterの値はYAMLのトップレベルmappingとする。複雑な入れ子mapping、配列、複数行文字列はMVPでは使わない。
- `id` は必須の非空文字列で、`[A-Za-z][A-Za-z0-9_-]*` に一致しなければならない。大文字・小文字は区別する。
- `kicker` は任意の非空文字列である。存在する場合も表示タイトルを兼ねない。
- `lang` は任意の非空言語タグ文字列である。指定する場合はBCP 47の言語タグとして解釈できる値にする。
- MVPで認識するトップレベルキーは `id`、`kicker`、`lang` の3つだけである。`link` など未知のキー、null、数値、配列はエラーとする。
- `id` の文書間重複は、複数文書を束ねるビルド構成の責務であり、本書の単一文書文法では判定しない。

frontmatterの構文が壊れている、`id` がない、値の型が違う、未知のキーがある場合は、通常のMarkdownとしてフォールバックせずエラーにする。

### 2.3 章タイトル

- frontmatter直後の最初の非空Markdown要素は、章タイトルを表すH1でなければならない。
- 章タイトルは通常のMarkdownのH1に、唯一の属性マーカー `.scene-title` を付けて記述する。
- 文書内にH1は1つだけ許可する。H1の本文は空であってはならない。
- `# タイトル` のように `.scene-title` を省略したH1、複数のH1、専用のタイトルブロックによる代替は正本ではエラーとする。
- H2からH6は通常のMarkdownとして使用できる。専用ブロック内でもH1は使えない。

属性マーカーの `.scene-title` は入力上の章タイトル識別子である。`section-title` という旧ブロック名を使ってはならない。

## 3. 専用ブロックの共通文法

### 3.1 開始・終了

専用ブロックの開始行は、次の形式に限る。

```text
:::<name>{<attribute-list>}
```

終了行は、列1から始まる単独の `:::` に限る。

```text
:::
```

開始行と終了行の前後に余分な文字を置いてはならない。終了行にブロック名を書いたり、属性を付けたりしない。開始行から終了行までがそのブロックの本文である。

`<name>` はASCII小文字、数字、ハイフンで構成する名前であり、MVPでは次の8語だけを認識する。

```text
dialogue  roleplay  choice  check  info  e-lois  battle  combo
```

名前は大文字・小文字を区別する。`Dialogue`、`e_lois`、`serif` のような表記は別名として扱わない。

### 3.2 属性リスト

属性リストは開始行の `{` と `}` の間に置く。属性は空白で区切る `key=value` の組であり、カンマ区切り、YAML、JSON、本文のMarkdownではない。

```text
:::check{title="衝動判定" skill="〈意志〉" difficulty=8 mandatory=true}
```

属性名はASCII小文字で始まる `[a-z][a-z0-9-]*` とする。属性名の重複、未知の属性、値のない属性、属性リスト内のカンマはエラーである。

属性値の型は次の3つだけである。

| 型 | 記法 | 規則 |
| --- | --- | --- |
| 文字列 | `"文字列"` | 改行を含めない。空白を含める場合も二重引用符で囲む。 |
| 整数 | `0`、`12` | ASCII数字のみ。符号、小数、単位は値に含めない。 |
| 真偽値 | `true`、`false` | 小文字の2値だけを使う。 |

文字列中では `\"` を二重引用符、`\\` をバックスラッシュとして扱う。それ以外のバックスラッシュ表記はエラーである。属性値の解釈は属性の型に従い、文字列を暗黙に整数や真偽値へ変換しない。

全ブロックで `title` は必須の文字列属性である。空文字列、未引用の日本語、本文中の最初の見出しをタイトルとして代用する記法は許可しない。`title` は表示用のプレーンテキストであり、属性値の中にMarkdownを記述しない。

### 3.3 本文

- 本文は開始行の次の行から終了行の直前までである。先頭・末尾の空行はMarkdownの通常規則に従って扱う。
- 本文は空であってはならず、Markdownとして少なくとも1つのブロック要素を生成しなければならない。
- 本文で使えるのは、段落、強調、インラインコード、改行、引用、順序付き・順序なしリスト、表、リンク、画像、H2からH6の見出し、コードブロック、水平線など、採用するMarkdown方言の標準構造である。
- 本文中の `[技能]` のような旧原稿由来の行は、専用属性ではなく通常のMarkdown本文として扱う。意味を持つ属性にしたい場合は、該当ブロックの開始行の属性として定義する。
- 専用ブロックの開始行は、通常のMarkdownの流れの中でだけ認識する。フェンスドコードブロックやインデントコードブロック内の `:::` はコードの内容であり、専用ブロックの開始・終了ではない。
- 専用ブロックの開始行を、別の専用ブロックの本文の通常フロー位置に置いてはならない。MVPでは専用ブロックの入れ子を禁止する。
- H1は本文に置けない。その他のMarkdown見出しやリストの入れ子は、専用ブロックの入れ子とは区別して、標準Markdownの構造として許可する。

raw HTMLタグ、HTMLコメント、HTML断片を専用ブロックの代わりに使う記法は正本に含めない。`<div class="...">` などを見つけても、専用ブロックとして解釈したり、後処理で意味を付けたりしてはならない。HTMLの具体的な出力はHTML出力契約で扱う。

### 3.4 エスケープと境界

- 列1の単独の `:::` は常に現在の専用ブロックの終了行である。ブロック外に現れた場合は余分な終了記号としてエラーにする。
- ブロック本文または通常Markdown中に、列1から始まる文字列 `:::` を文字として書きたい場合は、先頭にバックスラッシュを1つ付ける。たとえば `\:::example` は、専用構文ではなく文字列 `:::example` になる。
- この専用エスケープは通常のMarkdownの流れにだけ適用し、コードブロック内の文字列は変更しない。
- `\:::` は文字列 `:::` であり、終了行にはならない。終了行を表示するコード例はコードブロック内に置くか、このエスケープを使う。
- 開始行らしき文字列をエスケープしても、本文中に専用ブロックとして再解釈されない。未知名を通すための回避策にはならない。
- 属性値のエスケープは3.2節の規則だけを使う。本文内のバックスラッシュやMarkdownのエスケープは、属性値とは別に標準Markdownの規則で処理する。

### 3.5 標準Markdownとの境界

専用ブロック以外のテキストは標準Markdownとして解釈する。専用構文が優先されるのは、列1の開始行、列1の終了行、章タイトルの `.scene-title` だけである。Markdownのリンク、画像、表、通常の見出しを、専用属性や専用ブロック名として推測してはならない。

一方、`:::unknown`、`:::serif`、`:::section-title`、`:::toc`、`:::trailer` は標準Markdownへの無害なフォールバックを行わず、未知の専用記法としてエラーにする。未知の記法をHTML断片へ変換する実装も認めない。

## 4. ブロック別仕様

全ブロックで `title` は必須であり、本文は1つ以上の標準Markdownブロックを持つ。下表の「追加属性」以外の属性は許可しない。

| ブロック | `title` の意味 | 追加属性 | 本文の規則 |
| --- | --- | --- | --- |
| `dialogue` | 台詞を発する人物・主体 | なし | 台詞、ト書き、段落などを標準Markdownで記述する。複数の段落を話者の発言単位として使える。 |
| `roleplay` | 自由演技・進行指示の見出し | なし | プレイヤーやGMへの指示を標準Markdownで記述する。 |
| `choice` | 選択・分岐の見出し | なし | 少なくとも1つのリストを含める。リスト項目が選択肢であり、前後の説明文も置ける。 |
| `check` | 判定の見出し | `skill`、`difficulty` 必須。`mandatory` 任意 | 判定の成功・失敗時の処理や演出を標準Markdownで記述する。 |
| `info` | GM向け情報の見出し | なし | 情報、段階別の結果、補足を標準Markdownで記述する。必要な一覧や表は本文に置く。 |
| `e-lois` | Eロイス名・処理の見出し | なし | Eロイスの効果、対象、処理を標準Markdownで記述する。 |
| `battle` | 戦闘の見出し | なし | 敵、配置、終了条件、備考などを標準Markdownで記述する。小見出し名は固定しない。 |
| `combo` | コンボ名 | なし | 構成、タイミング、対象、射程、判定、効果などを標準Markdownで記述する。項目の表現は固定しない。 |

### 4.1 `check` の追加属性

`check` だけは、判定の機械可読な最低限の情報を開始行に置く。

- `skill`: 必須の非空文字列。技能名や判定能力を記述する。
- `difficulty`: 必須の0以上の整数。難易度を記述する。`8` は許可するが、`8+`、`8 ★`、`八` は許可しない。
- `mandatory`: 任意の真偽値。シナリオ進行上の必須判定なら `true` とする。省略時は `false` とする。

判定結果の説明や、成功時・失敗時の処理は本文に置く。`[技能]`、`[難易度]`、`★` を本文から正規表現で拾って属性を補完してはならない。

### 4.2 正常例と代表的なエラー例

以下の例は、各ブロックの最小限の正常形と代表的なエラーを示す。エラー例は説明用のため実行してはならない。

#### `dialogue`

`title` が話者名になる。話者を別の暗黙属性から推測しない。

```markdown
:::dialogue{title="渚"}

「おはよー、PC①。」

「今日のお昼、一緒に食べよ。」
:::
```

```markdown
:::dialogue
「話者名がないため、title 属性不足」
:::
```

この例は必須 `title` の不足でエラーになる。

#### `roleplay`

```markdown
:::roleplay{title="ふたりと渚"}

PCふたりと渚の会話を自由にロールプレイする。
:::
```

```markdown
:::roleplay{title="ふたりと渚"}

:::dialogue{title="渚"}
「専用ブロックを入れ子にしている。」
:::
:::
```

この例はMVPで禁止する専用ブロックの入れ子でエラーになる。コードブロック内に書かれた例は入れ子とはみなさない。

#### `choice`

```markdown
:::choice{title="《砕け散る絆》の対象"}

クロの攻撃を誰が受けるかを相談して決定する。

1. PC①が対象になる。
2. PC②がPC①をかばい、代わりに対象になる。
:::
```

```markdown
:::choice{title="行動を選ぶ"}

選択肢が文章だけで、リストが存在しない。
:::
```

この例は `choice` に必要な選択肢リストがないためエラーになる。

#### `check`

```markdown
:::check{title="衝動判定" skill="〈意志〉" difficulty=8 mandatory=true}

即座に侵蝕率が2D10点上昇する。判定に失敗した場合、暴走を受ける。
:::
```

```markdown
:::check{title="衝動判定" skill="〈意志〉"}

難易度が開始行にない。
:::
```

この例は必須 `difficulty` の不足でエラーになる。`difficulty="8"` のように文字列で書く場合も型不正としてエラーになる。

#### `info`

```markdown
:::info{title="魔法使いの正体"}

| 判定 | 難易度 | 結果 |
| --- | ---: | --- |
| 〈情報: UGN〉 | 15 | 背理天賦の正体が分かる。 |
| 〈情報: UGN〉 | 18 | 過去の事件記録にも到達する。 |
:::
```

```markdown
:::info{title="魔法使いの正体" audience="GM"}

未知の `audience` 属性を追加している。
:::
```

この例は `info` が許可する属性以外を含むためエラーになる。GM向けであることはブロック種別が表し、`audience` はMVP属性ではない。

#### `e-lois`

```markdown
:::e-lois{title="《衝動侵蝕: 妄想》"}

判定に失敗した場合、バッドステータスの暴走を受ける。
:::
```

```markdown
:::e-lois{title=""}

タイトルが空文字列である。
:::
```

この例は `title` が非空文字列でないためエラーになる。

#### `battle`

```markdown
:::battle{title="ミドル戦闘"}

##### エネミー

璃朱人のみ。

##### 戦闘終了条件

璃朱人の戦闘不能。
:::
```

```markdown
:::battle{title="ミドル戦闘"}

本文の終端がない。
```

この例はファイル末尾までに `:::` がないため閉じ忘れでエラーになる。

#### `combo`

```markdown
:::combo{title="黙示録の雨"}

| 項目 | 値 |
| --- | --- |
| タイミング | メジャーアクション |
| 対象 | シーン（選択） |
| 判定 | 10dx7+5 |

エフェクトによる射撃攻撃。攻撃力は+5。
:::
```

```markdown
:::combo{title="黙示録の雨" skill="自動"}

このブロックで定義されていない属性を指定している。
:::
```

この例は `combo` に追加属性がないためエラーになる。コンボの項目を機械可読にする必要が生じた場合は、将来の仕様更新で属性を追加し、本文の既存表現を暗黙に推測しない。

## 5. エラー規則

### 5.1 必ずエラーにする事象

buildとpreviewは、次の事象を警告だけで通過させてはならない。

- frontmatterの開始・終了、YAML mapping、必須 `id`、値の型が不正である。
- 章タイトルのH1がない、`.scene-title` がない、H1が複数ある、またはH1が空である。
- 8語彙以外の専用ブロック名がある。
- 開始行の属性リストが壊れている、必須属性がない、型が違う、値が空である。
- ブロックの終端 `:::` がない、ブロック外に余分な `:::` がある、終了位置が解釈できない。
- 専用ブロックの入れ子がある。
- 本文が空、または本文が標準Markdownとして解釈できない。
- `choice` に選択肢リストがない。
- `.scene-title` 以外のH1属性、専用ブロックの未知属性、属性名の重複がある。
- raw HTMLや、旧記法を意味的HTMLへ変換するための未定義のHTML断片がある。

### 5.2 診断と共通動作

エラーには可能な限り、原稿ファイル、行・列、ブロック名、原因、修正の方向を含める。たとえば `docs/chapters/md04.md:18:1: check: required attribute "difficulty" is missing` のように、作者が開始行を直ちに特定できる形にする。

buildとpreviewは同じ解析・検証を通し、エラー時は非成功の終了結果を返す。エラー入力に対して成功扱いの新しいHTMLやPDFを公開してはならない。旧名を推測して補完したり、未知の記法を通常のHTMLへフォールバックしたりしない。

## 6. 旧記法からの移行

giftの旧原稿では、[`_postReplaceList.json`](../gift/_postReplaceList.json) にある正規表現置換によって、`:::serif 渚` のような記法をHTMLへ変換している。これは新しい正本の文法ではない。旧原稿の変換は一回限りの移行ツールで行い、通常のbuild・previewに旧名の互換分岐を残さない。

| giftの旧記法 | 新しい正本 | 移行時の扱い |
| --- | --- | --- |
| `:::serif 渚` | `:::dialogue{title="渚"}` | `serif` を `dialogue` に変更し、タイトルを引用文字列にする。 |
| `:::rp ふたりと渚` | `:::roleplay{title="ふたりと渚"}` | `rp` を `roleplay` に変更する。 |
| `:::select 答` | `:::choice{title="答"}` | `select` を `choice` に変更する。選択肢リストは本文に残す。 |
| `:::check 衝動判定` | `:::check{title="衝動判定" skill="〈意志〉" difficulty=8}` | 本文の `[技能]` と `[難易度]` を属性へ移す。旧 `★` は `mandatory=true` に移す。 |
| `:::info 魔法使いの正体` | `:::info{title="魔法使いの正体"}` | 本文は標準Markdownとして移す。複数の判定結果は表やリストで表す。 |
| `:::e-lois 《砕け散る絆》` | `:::e-lois{title="《砕け散る絆》"}` | ブロック名を維持し、開始行を新文法にする。 |
| `:::battle ミドル戦闘` | `:::battle{title="ミドル戦闘"}` | 本文の小見出しや画像参照は標準Markdownとして移す。 |
| `:::combo 黙示録の雨` | `:::combo{title="黙示録の雨"}` | 項目は本文の表・リスト・段落として移す。 |
| `:::section-title ...` | frontmatterの `id` / `kicker` と `# タイトル {.scene-title}` | タイトル用ブロック自体は削除する。 |

`serif`、`rp`、`select` は新正本では不可であり、同じ名前を新ブロックの別名として受け付けない。`section-title`、`trailer`、`toc`、説明リスト、改ページ用の置換も新正本の専用構文には含めない。

旧記法から移行できない曖昧なタイトル、属性、本文は、推測で書き換えず、入力位置と移行できない理由を報告する。移行後のファイルは、この仕様の通常Markdownとしてレビューでき、通常のbuildで再検証できなければならない。

## 7. 章以外の一般文書

MVPで専用に定義するのは章原稿の外枠と8種類のブロックだけである。目次、NPC一覧、トレーラー、アペンディクスなどを、旧原稿に存在するという理由だけで個別の専用ブロックやfrontmatterスキーマへ分解しない。

これらの一般文書は、当面は通常Markdownとして記述する。文書をビルド対象にする場合は、章文書と同じfrontmatterと通常のH1を使えるが、`toc`、`trailer`、`section-title` などの旧名に意味を与えない。専用のナビゲーション、NPCデータ、トレーラー表示、説明リストが必要になった時点で、記法仕様・HTML出力契約・検証フィクスチャを同時に更新する。

この範囲制限により、一般文書ごとの場当たり的な例外、旧HTMLクラスへの依存、buildだけが受け付ける隠れた記法をMVPへ持ち込まない。

## 8. 実装上の不変条件

- 入力の専用ブロックはASTまたは同等の構造化解析段階で認識・検証し、生成HTMLへの正規表現置換で意味を付与しない。
- パーサーは、ブロック名、属性、本文、開始位置、終了位置を保持する。本文中の通常Markdownは、意味を失わずに下流へ渡す。
- `title`、`skill`、`difficulty`、`mandatory` の検証は、HTMLやThemeの責務へ委ねない。
- Themeはこの仕様の文法、旧記法、属性補完、エラー回復を解釈しない。
- HTML要素、クラス、`data-*` 属性、ARIA、改ページ、フォント、A5の余白は `docs/html-contract.md` およびThemeの仕様で扱う。
