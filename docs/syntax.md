# Markdown正本の記法仕様

## 1. 位置付けと適用範囲

本書は、TRPGシナリオを編集するMarkdown正本のMVP記法を定める。前提は
[要件定義書](requirements.md)であり、参照した旧原稿の実例は
[`gift/manuscripts/md4.md`](../gift/manuscripts/md4.md)、
[`gift/manuscripts/cl1.md`](../gift/manuscripts/cl1.md)、
[`gift/manuscripts/md3.md`](../gift/manuscripts/md3.md)、
[`gift/_postReplaceList.json`](../gift/_postReplaceList.json)である。

本文用 narrative block は次の7種類だけである。

`dialogue`、`roleplay`、`choice`、`check`、`info`、`e-lois`、`battle`

`combo`、`enemy` などの構造本質データは本文用ブロックではない。MVPでは敵データを `data/enemies/<enemy-id>.yaml` に置き、その `enemy.combos[]` にコンボを置く。Markdownでは敵全体をfragmentなし、コンボ単体を `#<combo-id>` fragment付きの通常リンクで参照する。`data/combos` は将来の共通combo拡張に限る。YAMLの詳細スキーマは、別途 `docs/data-contract.md` で定める。JSONを手書き正本にはしない。

本書が規定するのは、入力Markdownの文法、表示タイトル、専用フィールドの型と解釈範囲、本文の許可範囲、エラー条件、旧記法からの境界レベルの移行方針である。Unifiedのノード名、プラグインAPI、利用ライブラリの関数、変換アルゴリズムは規定しない。どの実装でも、同じ入力から同じブロック名・表示タイトル・専用フィールド・本文・位置を得られなければならない。

専用ブロックを表すHTML要素、クラス、`data-*` 属性、ARIA属性、CSSおよび組版上の見た目は、別途 `docs/html-contract.md` で定める。本書の表示タイトルやフィールド名を、出力HTMLのタグ名やクラス名と同一視してはならない。

## 2. 文書の外枠

### 2.1 章文書の標準形

MVPの章文書は、先頭のYAML frontmatter、frontmatter直後の最初の通常H1による章タイトル、その後のMarkdown本文からなる。正本の推奨形は次のとおりである。

```markdown
---
id: MD-04
kicker: ミドルフェイズ・シーン4
lang: ja
---

# Illegal Gifter

本文または通常のMarkdown。

:::dialogue 渚

「おはよー、PC①。」
:::
```

frontmatterは文書の機械可読なメタデータであり、表示上の章タイトルの代用ではない。`kicker` は章タイトルを補足するメタデータであり、H1に置き換えてはならない。`kicker` の表示方法はHTML出力契約の責務である。

### 2.2 frontmatter

- frontmatterはファイルの先頭（任意のUTF-8 BOMを除く）に、単独行の `---` で開始し、次の単独行の `---` で終了する。
- frontmatterの値はYAMLのトップレベルmappingとする。複雑な入れ子mapping、配列、複数行文字列はMVPでは使わない。
- `id` は必須の非空文字列で、`[A-Za-z][A-Za-z0-9_-]*` に一致しなければならない。大文字・小文字は区別する。
- `kicker` は任意の非空文字列である。存在する場合も表示タイトルを兼ねない。
- `lang` は任意の非空言語タグ文字列である。指定する場合はBCP 47の言語タグとして解釈できる値にする。
- MVPで認識するトップレベルキーは `id`、`kicker`、`lang` の3つだけである。未知のキー、null、数値、配列はエラーとする。
- `id` の文書間重複は、複数文書を束ねるビルド構成の責務であり、本書の単一文書文法では判定しない。

frontmatterの構文が壊れている、`id` がない、値の型が違う、未知のキーがある場合は、通常のMarkdownとしてフォールバックせずエラーにする。

### 2.3 章タイトル

- frontmatter終了行の後、空行を除いて最初に現れるMarkdown要素は、章タイトルを表す通常のH1でなければならない。
- 文書内にH1は1つだけ許可する。H1の本文は空であってはならない。
- 章タイトルは `# タイトル` のような通常のMarkdownで記述する。`.scene-title` を含む属性、属性リスト、クラス指定は使用しない。
- H2からH6は通常のMarkdownとして使用できる。専用ブロック内でもH1は使えない。
- `section-title` 等の専用タイトルブロックを章タイトルの代わりに使ってはならない。

## 3. 専用ブロックの共通文法

### 3.1 開始・終了

専用ブロックの開始行は、次の形式に限る。種別と表示タイトルの間の水平空白は、半角空白またはタブを1個以上置き、個数は任意とする。

```text
<start-line> ::= ":::" <name> <hspace> <display-title>
<name> ::= "dialogue" | "roleplay" | "choice" | "check" | "info" | "e-lois" | "battle"
<hspace> ::= (" " | "\t")+
<display-title> ::= 行末までの、空白を除いて空でないプレーンテキスト
```

したがって、通常の開始行は次のようになる。

```markdown
:::dialogue 渚
:::roleplay ふたりの日常
:::choice 《砕け散る絆》の対象
:::check 衝動判定
```

`<display-title>` は行末までを1つの表示タイトルとして扱う。タイトル内の日本語、ASCII文字、記号、複数の単語、全角空白は許可する。前後の半角空白・タブは区切りまたは行末空白として扱う。タイトル内のMarkdown、リンク、属性、引用、改行は解釈しない。

開始行に `{...}` の属性リストを付けてはならない。`title`、`skill`、`difficulty`、`mandatory` 等の属性名を開始行から読み取らない。表示タイトルらしくない属性リストを付けた旧記法は、タイトルとして黙って受理せずエラーにする。

終了行は、列1から始まる単独の `:::` に限る。

```text
<end-line> ::= ":::"
```

終了行にブロック名、表示タイトル、属性、空白以外の文字を置いてはならない。開始行から終了行までがそのブロックの本文である。開始行と終了行は通常Markdownのコードフェンス内では認識しない。

### 3.2 名前と表示タイトルの字句規則

- ブロック開始記号は列1の `:::` でなければならない。
- `<name>` はASCII小文字、数字、ハイフンで構成する候補名として読み取る。MVPで受理する名前は3.1節の7語だけである。
- 名前は大文字・小文字を区別する。`Dialogue`、`e_lois`、`serif` は別名として扱わない。
- 名前と表示タイトルの間に必要な水平空白がない、表示タイトルが空、または行末までに属性構文を置いた開始行は構文エラーとする。
- 表示タイトルを本文の最初の見出し、frontmatterの値、旧タイトルブロックから推測して補完しない。
- `:::combo 名前`、`:::enemy 名前` は未知の本文用ブロックとしてではなく、構造化データを本文ブロックで表そうとした予約名として診断する。対応するYAMLと通常リンクへ移行する。

### 3.3 本文

- 本文は開始行の次の行から終了行の直前までである。先頭・末尾の空行はMarkdownの通常規則に従って扱う。
- 本文は空であってはならず、Markdownとして少なくとも1つのブロック要素を生成しなければならない。
- 本文で使えるのは、段落、強調、インラインコード、改行、引用、順序付き・順序なしリスト、表、リンク、画像、H2からH6の見出し、コードブロック、水平線など、採用するMarkdown方言の標準構造である。
- 本文中の太字、引用、通常のリンク、画像、表、リストから、話者、判定、情報、戦闘、敵、コンボ等の専用意味を推測しない。
- H1は本文に置けない。その他のMarkdown見出しやリストの入れ子は、専用ブロックの入れ子とは区別して、標準Markdownの構造として許可する。
- 専用ブロックの開始行を、別の専用ブロックの本文の通常フロー位置に置いてはならない。MVPでは専用ブロックの入れ子を禁止する。

### 3.4 専用フィールドの認識境界

角括弧ラベルは、文書全体の置換規則ではない。実装は専用ブロックをASTとして確定した後、その直下にあるMarkdown ASTの要素だけを調べる。

フィールドとして解釈する行は、次の条件をすべて満たすものに限る。

1. 専用ブロックの本文直下にある。
2. 列1から始まる。
3. 1行だけのラベル行で、`[ラベル]` の後に水平空白と値が続く。または、ブロック種別が許す単独の `[必須]` である。
4. そのブロック種別で定義された既知ラベルである。

AST上のフィールドノードには、ブロック種別、ラベル名、値、入力位置を保持する。フィールドの値は1行の人間可読テキストまたはインラインMarkdownとして扱い、複数行の説明は通常の段落にする。

ラベル行が連続している場合も、行境界を保持した専用ブロックのASTでは各行を別々のフィールドノードとして扱う。空行の有無によって、技能/難易度ペアの境界やフィールドの意味を変えてはならない。これは専用ブロック内のAST拡張として行い、文書全体の正規表現置換では実装しない。

次の行は専用フィールドにならない。

```markdown
**[技能]** 〈知覚〉
> [技能] 〈知覚〉
- [技能] 〈知覚〉
    [技能] 〈知覚〉
```

これらはそれぞれ通常のMarkdownの強調、引用、リスト、インデントされた内容であり、`[技能]` の機械可読値や情報フィールドには変換しない。コードフェンス内の同じ文字列もコードの内容である。

専用ブロック直下の列1に、ラベル形式に見える未知の名前が現れた場合は、通常の段落へフォールバックせず未知の予約フィールドとして診断する。文字として書きたい場合は、通常Markdownのエスケープ、引用、リスト、コード等を使う。専用ブロック外の角括弧行には、この専用フィールド規則を適用しない。

### 3.5 既知ラベルのMVP一覧

既知ラベルは文書全体の共通置換表ではなく、ブロック種別ごとのASTスキーマである。

| ブロック | 既知ラベル | 解釈 |
| --- | --- | --- |
| `dialogue` | なし | 話者名は開始行の表示タイトルで表す。フィールドが必要な場合は通常の文章で書く。 |
| `roleplay` | `対象`、`条件`、`備考` | 人間可読の補足フィールド。 |
| `choice` | `対象`、`条件`、`分岐`、`備考` | 選択対象や分岐の補足フィールド。本文にリストを要求しない。 |
| `check` | `技能`、`難易度`、`必須`、`成功時`、`失敗時`、`備考` | 開始フェンス後の空行を除く先頭から連続するフィールド前置部にある、ちょうど1組の `技能`/`難易度`/任意の `必須` は機械可読。その他は人間可読。 |
| `info` | `技能`、`難易度`、`必須`、`対象`、`条件`、`成功時`、`失敗時`、`備考` | すべて人間可読フィールド。技能/難易度は複数ペアを許容する。 |
| `e-lois` | `技能`、`難易度`、`必須`、`対象`、`条件`、`備考` | 人間可読フィールド。技能/難易度は複数ペアを許容する。 |
| `battle` | `エネミー`、`配置`、`戦闘終了条件`、`参照`、`備考` | 敵の本質データは値に埋め込まず、YAMLへの通常リンクを使う。 |

既知ラベルの値は、空であってはならない。ただし `check` の `[必須]` と、`info`・`e-lois` で旧原稿の必須性を人間可読に残す `[必須]` は単独行を許可する。`info`・`e-lois` の `[必須]` は `check` の機械可読フラグとは別の表示フィールドである。

## 4. ブロック別仕様

### 4.1 `dialogue`

表示タイトルが台詞を発する人物・主体になる。話者名を本文や太字から推測しない。

```markdown
:::dialogue 渚

「おはよー、PC①。」

「今日のお昼、一緒に食べよ。」
:::
```

表示タイトルがない開始行はエラーになる。

```markdown
:::dialogue
「話者名がない。」
:::
```

### 4.2 `roleplay`

```markdown
:::roleplay ふたりと渚

PCふたりと渚の会話を自由にロールプレイする。

[対象] PC①、PC②、渚
:::
```

`roleplay` 内の `[対象]` は、列1の既知ラベル行として人間可読フィールドになる。引用や太字にした場合はフィールドにならない。

### 4.3 `choice`

選択対象や分岐は、自然文、段落、リスト、表など作者が読みやすい通常Markdownで記述できる。リストは必須ではない。

```markdown
:::choice 《砕け散る絆》の対象

クロの攻撃を誰が受けるかを相談して決定する。PC①が受けるならそのまま進み、PC②がかばうならPC②を対象にして次の戦闘へ進む。
:::
```

リストを使う場合も通常Markdownとして扱う。

```markdown
:::choice 行動を選ぶ

1. 渚を説得する。
2. クロの要求を受け入れる。
3. その場から退く。
:::
```

### 4.4 `check`

`check` は、開始フェンス後の空行を除く先頭から連続するフィールド前置部に、技能/難易度ペアをちょうど1組置く。機械可読項目は開始行の属性ではなく、次の専用フィールド行から得る。

```markdown
:::check 衝動判定

[技能] 〈意志〉
[難易度] 8
[必須]

即座に侵蝕率が2D10点上昇する。判定に失敗した場合、暴走を受ける。
:::
```

`[必須]` は値を持たない単独行で、この1組に付く。省略時はその判定を必須とはしない。複数の判定方法や情報収集項目を同じ `check` にまとめず、必要なら別の `check` または `info` として記述する。

機械可読フィールドの規則は次のとおりである。

- 開始フェンス直後の空行を読み飛ばした最初の非空行は `[技能] 値` でなければならない。
- その次の非空行は `[難易度] 0以上の整数` でなければならない。次の非空行に限り、任意で単独の `[必須]` を置ける。
- 上記の行列は、空行だけを挟んで連続するフィールド前置部を構成する。前置部の後から通常Markdown本文を開始できる。
- 通常Markdown本文が始まった後に `[技能]`、`[難易度]`、`[必須]` を置いてはならない。2組目の技能/難易度を前置部または本文に置くこともエラーである。
- `[技能]` は、行末までの空白を除いて空でない技能名・判定能力である。
- `[難易度]` はASCII数字による0以上の整数である。`0`、`8`、`12` は許可する。`8+`、`8 ★`、`八`、空文字列は許可しない。
- `[必須]` は `[難易度]` の後に値なしで1回だけ置ける。

### 4.5 `info`

`info` の角括弧ラベルは、人間可読フィールドとしてASTに保持する。`check` のように1つの判定だけへ制限せず、複数の技能/難易度ペアを順序付きで記述できる。

```markdown
:::info 野原球児

[技能] 〈情報: 噂話〉
[難易度] 5
[必須]

[技能] 〈情報: UGN〉
[難易度] 8

野原球児が強制的に能力を引き出されたジャームであることが分かる。
:::
```

この例の2組は別々の人間可読フィールド組として保持する。`info` の `[必須]` は表示用フィールドであり、`check` の機械可読フラグへ暗黙変換しない。技能行だけ、難易度行だけ、または対応順が崩れた組はエラーにする。

### 4.6 `e-lois`

```markdown
:::e-lois 《衝動侵蝕: 妄想》

[技能] 〈意志〉
[難易度] 8

判定に失敗した場合、バッドステータスの暴走を受ける。
:::
```

Eロイス名は開始行の表示タイトルである。本文の太字見出しや `[名称]` 行から名前を推測しない。技能/難易度フィールドを使う場合は、`info` と同じく複数ペアを許容する人間可読フィールドとする。

### 4.7 `battle`

戦闘の進行や配置は通常Markdownまたは既知ラベルで記述する。敵の本質データは外部YAMLに置く。

```markdown
:::battle ミドル戦闘

[エネミー] 璃朱人
[配置] 体育館の中央。PCは入口側。
[参照] [敵データ：璃朱人](../data/enemies/liszt.yaml)

##### 戦闘終了条件

璃朱人の戦闘不能。
:::
```

外部データへのリンクは通常のMarkdownリンクであり、本文ブロックの入れ子や独自の敵記法ではない。YAMLの項目、ファイル配置、存在確認、スキーマ検証は `docs/data-contract.md` で定める。

### 4.8 外部構造化データへの通常リンク

敵・コンボ等を参照する最小のMarkdown表現は、次のような通常リンクである。

```markdown
[敵データ：シロ](../data/enemies/shiro.yaml)
[コンボデータ：黙示録の雨](../data/enemies/shiro.yaml#apocalypse-rain)
```

リンクは素のMarkdown表示でも意味が分かる表示文字列にする。敵全体のリンクはfragmentなし、コンボ単体のリンクは `data/enemies/<enemy-id>.yaml#<combo-id>` とする。コンボはリンク先YAMLの `enemy.combos[]` に対応する。`data/combos` は将来の共通combo拡張に限る。`:::combo` のような本文ブロック、HTML断片、手書きJSONを代わりに使わない。詳細なデータ契約は本書の対象外であり、`docs/data-contract.md` に分離する。

## 5. 字句・境界規則

### 5.1 標準Markdownとの境界

専用構文が優先されるのは、列1の開始候補、列1の単独終了行、専用ブロック直下の既知ラベル行、frontmatter、章タイトルの通常H1だけである。

通常のMarkdownは、次の形式を専用の意味にしない。

- `**渚**` を話者名にする。
- `> [技能] 〈知覚〉` を判定フィールドにする。
- 敵全体は `[敵データ：名前](../data/enemies/<enemy-id>.yaml)`、コンボ単体は `[コンボデータ：表示名](../data/enemies/<enemy-id>.yaml#<combo-id>)` とする。それ以外の通常リンクを、敵やコンボの構造化データとして推測しない。
- 表の列見出しや太字を、`技能`、`難易度`、`必須`、`対象` 等の予約フィールドに置換しない。

一方、`:::unknown 名前`、`:::serif 渚`、`:::section-title 章`、`:::combo 黙示録の雨`、`:::enemy 璃朱人` は、通常Markdownへの無害なフォールバックを行わず診断する。`trailer`、`toc` 等の旧専用名もMVPの本文用語彙ではない。

### 5.2 終端とエスケープ

- 列1の単独の `:::` は、現在の専用ブロックの終了行である。ブロック外に現れた場合は余分な終了記号としてエラーにする。
- `:::` の後に空白や文字がある行は終了行ではない。専用ブロック内では不正な開始候補または本文として診断対象になる。
- ブロック本文または通常Markdown中に、列1から始まる文字列 `:::` を文字として書きたい場合は、先頭にバックスラッシュを1つ付ける。たとえば `\:::example` は専用構文ではなく文字列 `:::example` になる。
- `\:::` は文字列 `:::` であり、終了行にはならない。終了行を表示するコード例はコードブロック内に置くか、このエスケープを使う。
- この専用エスケープは通常のMarkdownの流れにだけ適用し、コードブロック内の文字列は変更しない。
- 開始行らしき文字列をエスケープしても、未知名を専用ブロックとして通すための回避策にはならない。

### 5.3 生HTML

raw HTMLタグ、HTMLコメント、HTML断片を専用ブロックの代わりに使う記法は正本に含めない。`<div class="...">` などを見つけても、専用ブロックとして解釈したり、後処理で意味を付けたりしてはならない。HTMLの具体的な出力はHTML出力契約で扱う。

## 6. エラー規則

### 6.1 必ずエラーにする事象

buildとpreviewは、次の事象を警告だけで通過させてはならない。

- frontmatterの開始・終了、YAML mapping、必須 `id`、値の型が不正である。
- frontmatter直後の最初のH1がない、H1が空である、H1が複数ある、H1に `.scene-title` や属性リストがある。
- 開始行に表示タイトルがない、名前とタイトルの区切りがない、タイトル行の形式が不正である。
- 開始行に属性リストがある、または `title`、`skill`、`difficulty`、`mandatory` 等の開始行属性を使っている。
- 7語以外の専用ブロック名、`combo`・`enemy` 等の本文で禁止された構造化データ予約名がある。
- 終端 `:::` がない、終端が列1でない、ブロック外に余分な終端がある、終了位置が解釈できない。
- 専用ブロックの入れ子がある。
- 本文が空、または本文を標準Markdownとして解釈できない。
- 専用ブロック直下の列1に未知の予約フィールドがある、既知フィールドの値が空である、フィールドの順序や位置が種別の規則に違反する。
- `check` の機械可読前置部が開始フェンス後の空行を除く先頭から連続していない、技能値が空、難易度が0以上の整数でない、ペアがない・未完、2組目がある、通常Markdown本文開始後に機械フィールドがある、`[必須]` が単独行でない、またはその位置が不正である。
- `info`、`e-lois` の技能/難易度ペアが未完である。複数ペアを1つにまとめたり、後続ペアを捨てたりしてはならない。
- 属性リスト、`.scene-title`、旧ブロック名を通常のbuild・previewで受理しようとする。
- YAML参照リンクの形式、相対パス、存在確認、スキーマ検証に違反する。詳細な診断項目は構造化データ契約で定める。
- ASTから意味的HTMLへ変換できない構造がある。

### 6.2 具体的な異常例

次の例は説明用であり、正本として実行してはならない。

```markdown
<!-- 表示タイトルがない -->
:::dialogue
「話者名がない。」
:::

<!-- 廃止した属性リスト -->
:::check{title="衝動判定" skill="〈意志〉" difficulty=8}
本文
:::

<!-- 難易度に単位・星印が混ざっている -->
:::check 判定
[技能] 〈知覚〉
[難易度] 8 ★
本文
:::

<!-- checkの技能/難易度が2組ある -->
:::check 2組の判定
[技能] 〈知覚〉
[難易度] 8

[技能] 〈情報: UGN〉
[難易度] 12
本文
:::

<!-- 本文ブロックではない予約名 -->
:::combo 黙示録の雨
本文
:::

<!-- 未知の予約フィールド -->
:::info 情報
[秘密度] 高
本文
:::
```

`[技能]` や `[難易度]` を太字、引用、リストにした場合に通常Markdownとして表示することと、`check` の必要フィールドを満たしていないためエラーにすることは両立する。変換器は見た目から機械可読項目を推測しない。

### 6.3 診断と共通動作

エラーには可能な限り、原稿ファイル、行・列、ブロック名、表示タイトルまたはフィールド名、原因、修正の方向を含める。たとえば次のような形式にする。

```text
docs/chapters/md04.md:18:1: check「衝動判定」: [難易度] must be a non-negative integer
docs/chapters/md04.md:42:1: info「情報」: unknown reserved field [秘密度]
```

buildとpreviewは同じ解析・検証を通し、エラー時は非成功の終了結果を返す。エラー入力に対して成功扱いの新しいHTMLやPDFを公開してはならない。旧名を推測して補完したり、未知の記法を通常のHTMLへフォールバックしたりしない。

## 7. 旧記法からの移行

giftの旧原稿にある次の記法は、新しい正本の文法ではない。旧原稿の変換は一回限りの移行ツールで行い、通常のbuild・previewに旧名の互換分岐を残さない。

| giftの旧記法 | 新しい正本 | 移行時の扱い |
| --- | --- | --- |
| `:::serif 渚` | `:::dialogue 渚` | 旧名を `dialogue` に変更し、行末の名前を表示タイトルとして残す。 |
| `:::rp ふたりと渚` | `:::roleplay ふたりと渚` | 旧名を `roleplay` に変更する。 |
| `:::select 答` | `:::choice 答` | 旧名を `choice` に変更する。選択対象や分岐は本文の自然文・リスト・表をそのまま使い、リストの追加を強制しない。 |
| `:::check 衝動判定` と本文の `[技能]` / `[難易度]` | `:::check 衝動判定` と同じ専用ラベル行 | 属性へ移さず、開始フェンス後の空行を除く先頭から連続するフィールド前置部にちょうど1組を置く。難易度行の `★` は行から取り除き、その組の直後に単独 `[必須]` を置く。旧 `check` に複数組がある場合は1つへ潰さず、移行エラーとして分割または `info`/`e-lois` 化を作者に求める。 |
| `:::info 魔法使いの正体` と複数の技能/難易度組 | `:::info 魔法使いの正体` と既知ラベル行 | `[技能]` / `[難易度]` の組を人間可読フィールドとして順序どおりに残す。複数組を1組にまとめない。旧 `★` を残す場合は `info` の単独 `[必須]` フィールドとして扱い、`check` の機械値へ変換しない。 |
| `:::e-lois 《砕け散る絆》` | `:::e-lois 《砕け散る絆》` | ブロック名を維持し、開始行を新文法にする。本文の既知ラベルを残す。 |
| `:::battle ミドル戦闘` | `:::battle ミドル戦闘` | 開始行を新文法にし、配置・終了条件・参照を通常Markdownまたは既知ラベルで残す。 |
| `:::combo 黙示録の雨` | `[コンボデータ：黙示録の雨](../data/enemies/<enemy-id>.yaml#<combo-id>)` | 本文ブロックは作らない。構成、タイミング、対象、射程、効果等を対応する敵YAMLの `enemy.combos[]` へ移し、Markdownはfragment付きの通常リンクで参照する。敵全体はfragmentなしで参照する。`data/combos` は将来の共通combo拡張に限る。詳細スキーマは `docs/data-contract.md` で定める。 |
| 敵データの旧HTMLリンク | `[敵データ：名前](../data/enemies/<enemy-id>.yaml)` | HTMLリンクをMarkdownの通常リンクへ直し、敵の本質データを `data/enemies/<enemy-id>.yaml` へ移す。 |
| `:::section-title ...`、`# タイトル {.scene-title}` | `# タイトル` | タイトルブロックと属性マーカーを削除する。frontmatterを維持し、frontmatter直後の最初の通常H1を章タイトルにする。 |
| `:::dialogue{title="渚"}` 等の属性リスト | `:::dialogue 渚` | 属性リストをタイトルへ機械的に残さず、表示タイトルだけを開始行の行末へ移す。未知属性や曖昧な値は移行エラーにする。 |

`serif`、`rp`、`select`、`combo`、`section-title`、`trailer`、`toc` 等は、新正本で同じ名前の別名として受け付けない。移行できない曖昧なタイトル、ラベル、属性、外部データは、推測で書き換えず、入力位置と移行できない理由を報告する。移行後のファイルは、この仕様の通常Markdownと外部YAML参照としてレビューでき、通常のbuildで再検証できなければならない。

## 8. 章以外の一般文書

MVPで専用に定義するのは章原稿の外枠と本文用 narrative blockだけである。目次、NPC一覧、トレーラー、アペンディクスなどを、旧原稿に存在するという理由だけで個別の専用ブロックやfrontmatterスキーマへ分解しない。

これらの一般文書は、当面は通常Markdownとして記述する。文書をビルド対象にする場合は、章文書と同じfrontmatterと通常のH1を使えるが、`toc`、`trailer`、`section-title` 等の旧名に意味を与えない。敵・コンボ一覧が必要な場合は、外部YAMLと通常リンクの境界を使う。専用のナビゲーション、NPCデータ、トレーラー表示が必要になった時点で、記法仕様・HTML出力契約・構造化データ契約・検証フィクスチャを同時に更新する。

## 9. 実装上の不変条件

- 入力のfrontmatter、章タイトル、本文用ブロック、専用フィールドはASTまたは同等の構造化解析段階で認識・検証し、生成HTMLへの正規表現置換で意味を付与しない。
- パーサーは、ブロック名、表示タイトル、本文、開始位置、終了位置、専用フィールド、外部リンク参照位置を保持する。本文中の通常Markdownは、意味を失わずに下流へ渡す。
- 開始行に属性リストを許可しない。`check` の技能、難易度、必須性は、開始フェンス後の空行を除く先頭から連続するフィールド前置部からのみ検証し、ちょうど1組に限定する。
- `info` 等の既知ラベルは専用ブロック直下・列1のAST要素だけから解釈し、文書全体の正規表現置換を行わない。複数の技能/難易度ペアを保持する。
- `combo`、敵本体などの構造化データを本文ブロックへ埋め込まず、YAML正本とMarkdown通常リンクの境界を維持する。JSONを手書き正本にしない。
- `choice` の本文にリストがないことをエラーにしない。
- Themeはこの仕様の文法、旧記法、フィールド補完、エラー回復を解釈しない。
- HTML要素、クラス、`data-*` 属性、ARIA、改ページ、フォント、A5の余白は `docs/html-contract.md` およびThemeの仕様で扱う。
