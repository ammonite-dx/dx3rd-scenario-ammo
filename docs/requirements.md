# TRPGシナリオ組版環境 要件定義書

## 1. 文書の位置付け

- 状態: MVP仕様改訂版
- 対象: TRPGシナリオをMarkdownで執筆し、意味的HTMLを経由してVivliostyleでPDF化する再利用可能な環境
- MVPの判型: A5
- 正本: シナリオのMarkdownと、そこから参照する構造化データのYAML
- 生成物: 中間HTML、PDF、`.vivliostyle` 作業領域

本書で決定したMVPの方針は、後続の記法仕様書・HTML出力契約・構造化データ契約・実装設計の前提とする。後続仕様で具体化する項目を保留事項として挙げる場合も、MVPの対象範囲や方針を未決定に戻すものではない。

## 2. 目的

シナリオ作者が、日本語の素のMarkdownを読み書きしながら、TRPGの進行に必要な会話、ロールプレイ指示、判定、情報、戦闘などを読みやすく組版したPDFを再現可能に生成できるようにする。

次の性質を同時に満たすことを目的とする。

1. Markdownを本文の唯一の正本とし、HTMLやPDFを手作業で維持しない。
2. シナリオ固有の記法を、正規表現による文書全体の置換ではなく、VFM/UnifiedのAST上で検証・変換する。
3. 変換結果を意味的HTMLとして保持し、A5の組版はThemeに分離する。
4. buildとpreviewで同じ変換・検証結果を得る。
5. 不正な記法、未知のブロック、未知の予約フィールドを黙って通さず、執筆時点で修正できる診断として報告する。
6. 敵やコンボの構造本質データはMarkdown本文から分離し、YAMLを正本として管理する。

## 3. スコープ

### 3.1 MVPに含めるもの

- 単一リポジトリ内で完結するMarkdown執筆環境
- 先頭のfrontmatterと、その直後の最初の通常H1による章タイトル
- VFM/Unifiedを基盤にしたASTベースの独自変換
- 本文用 narrative block の語彙
  `dialogue`, `roleplay`, `choice`, `check`, `info`, `e-lois`, `battle`
- 開始行の表示タイトルと単独の `:::` 終端を持つ、属性リストを使わない本文記法
- 専用ブロック内の既知の角括弧ラベル行を、ブロック直下のASTから人間可読フィールドとして扱う仕組み
- `check` の技能・難易度・必須マーカーと、ちょうど1組の技能/難易度ペアの検証
- 敵・コンボ等の構造化データを外部YAMLへ分離し、Markdownの通常リンクで参照する境界
- 専用ブロックを含むMarkdownから意味的HTMLを生成する変換ツール
- 変換ツールを利用したVivliostyle CLIのbuildとpreview
- A5 PDFの安定した生成
- PDF生成に用いた中間HTMLの出力
- 未知名、未知の予約フィールド、閉じ忘れ、開始行の形式不正、本文の不正、MVPで禁止する入れ子の検証
- CLI/VFMの検証済みバージョン固定と依存関係ロック
- Vivliostyleの `workspaceDir` として `.vivliostyle` を使用する構成
- 旧記法を新しい正本へ一度だけ変換する移行ツール
- オフラインでフォントを再現できる構成

### 3.2 MVPに含めないもの

- `combo` や `enemy` を本文用の専用ブロックとして解釈する仕組み
- 敵・コンボの詳細スキーマ。これは別文書 `docs/data-contract.md` で定める。
- JSONを手書き正本として管理する運用。JSONを生成物や交換形式として使う可能性は妨げない。
- 属性リストや `.scene-title` を新しい正本で受け付ける互換構文
- 旧記法をbuildまたはpreviewで恒久的に受け付ける互換層
- 本文全体の正規表現置換による角括弧ラベルの意味付け
- WebPub出力。これはMVP後の次段階で扱う。
- EPUB出力。現行計画の対象外とする。
- A4 PDFの対応およびA4向けの完成度保証。将来追加できる設計にはするが、MVPの完了条件には含めない。
- Markdown以外を本文の正本とする編集フロー
- ThemeがMarkdownの記法を解釈する仕組み
- MVP時点でのパッケージ分離。APIが安定した後に分離を検討する。

## 4. 用語

| 用語 | 定義 |
| --- | --- |
| Markdown正本 | 作者が編集・レビューするシナリオ本文。frontmatter、通常のMarkdown、本文用 narrative block、外部データへの通常リンクを含む。 |
| narrative block | 本文中でシナリオ進行上の意味を持つ専用ブロック。MVPでは `dialogue`、`roleplay`、`choice`、`check`、`info`、`e-lois`、`battle` を指す。 |
| 表示タイトル | narrative block の開始行に書く、行末までの必須のプレーンテキスト。話者名、判定名、情報項目名などに使う。 |
| 角括弧ラベル行 | 専用ブロック直下の列1から始まる、既知の `[ラベル] 値` 形式の行。ブロックごとのAST解釈対象であり、文書全体の置換対象ではない。 |
| VFM | Vivliostyle Flavored Markdown。現在のMarkdown入力を解析する基盤。 |
| Unified | MarkdownをASTとして扱う変換基盤。専用ブロックの認識・検証・変換はこのASTの段階で行う。 |
| AST | Markdownの構造を表す抽象構文木。文字列の正規表現置換で代用しない。 |
| 意味的HTML | 見た目だけでなく、見出し、節、段落、リスト、表、リンク、画像、専用ブロックの意味が構造として表現されたHTML。 |
| 構造化データ | 敵、コンボなどの機械処理を主目的とするデータ。Markdown本文から分離したYAMLファイルを正本とする。 |
| Theme | 意味的HTMLに対してページ寸法、書体、余白、改ページ、装飾などの組版を適用するCSS等の資産。 |
| CLI | Vivliostyleを実行してHTMLを組版し、PDFまたはプレビューを提供するコマンドライン実行部。 |
| build | Markdownと参照データを検証・変換し、中間HTMLとPDFを生成する処理。 |
| preview | buildと同じMarkdown変換・検証結果を閲覧する処理。 |
| 旧記法 | giftで使われているブロック名、属性リスト、タイトルブロック、星印など、新しい正本では採用しない記法。 |
| 移行ツール | 旧記法を一度だけ新しいMarkdownと外部YAMLへの参照へ変換する補助ツール。通常のbuild経路には含めない。 |

## 5. 参照元と確認できた事実

視覚・機能の参照元は、リポジトリ内の `gift` プロジェクトに限定する。確認できた事実は次のとおりであり、これを超える機能は本書の根拠にしない。

- [`gift/package.json`](../gift/package.json) には `build` と `preview` のスクリプトがあり、`@vivliostyle/cli` を依存関係としている。
- [`gift/vivliostyle.config.js`](../gift/vivliostyle.config.js) は判型をA5に設定し、Theme、複数のHTMLエントリ、`manuscripts` のエントリコンテキストを指定している。
- `gift/manuscripts` にはfrontmatter、`section-title`、通常のH1、`serif`、`rp`、`select`、`check`、`info`、`e-lois`、`battle`、`combo` 等の旧記法が確認できる。
- `gift/manuscripts/md1.md`、`md2.md`、`md3.md` などには、`[技能]`、`[難易度]`、`★` と複数の技能/難易度組を使う情報項目がある。
- [`gift/_postReplaceList.json`](../gift/_postReplaceList.json) は旧記法を正規表現でHTMLへ置換している。これは移行対象の確認にだけ使い、新環境の本文変換方式には引き継がない。
- [`gift/manuscripts/md4.md`](../gift/manuscripts/md4.md) と [`gift/manuscripts/md4.html`](../gift/manuscripts/md4.html) では、専用記法がHTMLの専用クラス付き要素に変換され、通常の見出しがHTMLのsectionと見出し要素として出力されている。
- [`gift/themes/vivliostyle-theme-dx3rd-ammonite/main.css`](../gift/themes/vivliostyle-theme-dx3rd-ammonite/main.css) はA5のページ寸法、見出し、専用クラス、改ページ、リンクのページ番号表示などを定義している。また、Google Fontsを外部URLから読み込んでいる。

以上を参照しつつ、新環境では旧タイトルブロック、属性リスト、本文用ではない `combo` ブロック、正規表現による後処理を正本の仕様から外し、本文の可読性と構造化データの境界を再設計する。

## 6. アーキテクチャ

### 6.1 処理の流れ

```text
Markdown + frontmatter + 外部YAML + 画像等の資産
        │
        ▼
VFM/Unifiedによる解析
        │
        ├── frontmatter / 最初のH1の検証
        ├── narrative blockの境界・表示タイトルの検証
        ├── 専用ブロック直下の既知ラベルとcheckペアの解釈
        └── YAML参照リンクの境界検証
        │
        ▼
ASTの検証・専用ノードの意味変換
        │
        ▼
意味的HTML（中間生成物）
        │
        ├── Vivliostyle CLI + Theme ──> A5 PDF
        └── preview ───────────────────> 同じ変換結果の閲覧
```

### 6.2 責務の分離

- **Markdown** は本文と文書構造を表す。作者が編集する本文の唯一の正本である。
- **frontmatter** は文書IDなどの機械可読メタデータを担う。表示上の章タイトルはfrontmatterに入れず、通常のH1で表す。
- **VFM/Unifiedと独自変換ツール** は、Markdownを解析し、narrative block、表示タイトル、専用フィールド、`check` の機械可読項目を検証して意味的HTMLへ変換する。認識はAST上で行い、生成HTMLへの正規表現後処理を使用しない。
- **外部YAML** は敵・コンボ等の構造化データの正本である。Markdownは相対パスの通常リンクで参照する。YAMLの詳細スキーマは `docs/data-contract.md` の責務とする。
- **意味的HTML** は、通常のMarkdown構造とnarrative blockの意味を保持する中間契約である。将来のWebPubなど、PDF以外の出力の基盤にもできる構造とする。
- **Theme** は意味的HTMLの組版だけを担当する。Markdownの記法、旧記法、属性の補完、ラベルの意味判断を担当しない。
- **Vivliostyle CLI** は、変換済みHTMLをA5に組版し、PDFとpreviewを提供する。
- **移行ツール** は、旧記法の入力を新しいMarkdownと外部YAMLへの参照へ変換する。通常の変換パイプラインとは別の一回限りの処理とする。

### 6.3 バージョンと作業領域

- CLIとVFMは、実際にbuild・preview・PDF出力を検証したバージョンを明示的に固定する。
- 依存関係のロックファイルをリポジトリで管理し、未検証の `latest` 追随を実行時の前提にしない。
- Vivliostyleの `workspaceDir` は `.vivliostyle` に固定する。キャッシュ、一時ファイル、CLIが生成する作業状態はここに集約し、Markdown正本と混在させない。
- MVPは単一リポジトリで完成させる。変換API、HTML出力契約、構造化データ契約が安定した後に、再利用単位を見極めてパッケージ分離を検討する。

## 7. 機能要件

### 7.1 原稿管理と章構造

- **FR-01**: シナリオ本文、frontmatter、narrative block、外部データへのリンクはMarkdownに記述する。
- **FR-02**: frontmatterはファイル先頭に維持し、文書IDや言語などのメタデータを置く。frontmatterは表示本文の代替にしない。
- **FR-03**: frontmatter終了後、空行を除いて最初に現れる通常のH1を章タイトルとする。章タイトルの表示文字列は生成HTMLとPDFへ反映する。
- **FR-04**: 文書内のH1は章タイトルの1つだけとする。`.scene-title` を含む見出し属性、専用タイトルブロック、後続のH1による代替は正本に含めない。
- **FR-05**: 通常のMarkdownの段落、見出し、リスト、表、リンク、画像、強調、引用等を、意味と内容を失わずにHTMLへ変換する。
- **FR-06**: 画像、YAMLなど原稿が参照する資産は、Markdownからの相対参照を維持できるようにする。生成HTMLやPDFを直接編集して参照を補正する運用は採用しない。

### 7.2 本文用 narrative block

- **FR-07**: MVPの本文用ブロック名は次の7種類に限定する。

  | ブロック | 用途 |
  | --- | --- |
  | `dialogue` | 登場人物等の台詞・会話を表す。開始行の表示タイトルは話者・主体名にする。 |
  | `roleplay` | プレイヤーが自由に演技する場面や進行指示を表す。 |
  | `choice` | 選択、分岐、選択対象、選択後の進行を表す。本文にリストを必須としない。 |
  | `check` | 技能、難易度、必須性、判定結果等を表す。機械可読項目は開始フェンス後の空行を除く先頭から連続するフィールド前置部から得る。 |
  | `info` | GM向けの情報、補足、複数の情報収集項目等を表す。 |
  | `e-lois` | Eロイスに関する処理や説明を表す。 |
  | `battle` | 戦闘の進行、配置、終了条件、参照先等を表す。敵の本質データ自体は外部YAMLに置く。 |

- **FR-08**: 開始行はブロック名と行末までの必須の表示タイトルで構成し、属性リストを持たない。終了行は列1の単独 `:::` とする。開始行、表示タイトル、終了位置はASTのノード情報として保持する。
- **FR-09**: 各ブロックの本文は標準Markdownとして解析できる1つ以上のブロック要素を持つ。本文内の段落、リスト、表、引用、強調、コードブロック等は通常Markdownの意味を保つ。
- **FR-10**: 専用ブロック直下の列1にある既知の角括弧ラベル行だけを、ブロック種別ごとのASTフィールドとして解釈する。本文全体の正規表現置換、列1以外の行の推測、文書外の一括置換は行わない。
- **FR-11**: `check` の機械可読項目は、開始フェンス後の空行を除く先頭から連続するフィールド前置部に、`[技能] 値` と `[難易度] 0以上の整数` をちょうど1組置く。任意の単独 `[必須]` はその1組に付く。通常Markdown本文の開始後や2組目の技能/難易度はエラーとし、属性リストから補完してはならない。
- **FR-12**: `info`、`e-lois` 等で扱う角括弧ラベルは人間可読フィールドとして保持する。`[技能]` と `[難易度]` を使う情報収集項目では、複数の技能/難易度ペアを順序を保ったまま扱える設計にする。これらを `check` の機械可読項目と同一視しない。
- **FR-13**: `choice` はリストの存在を必須条件にしない。本文に選択対象や分岐を自然文、段落、リスト、表など作者が読みやすい通常Markdownで記述できる。
- **FR-14**: 太字、引用、通常のリンク、画像、表などの標準Markdownから、専用の話者・判定・情報・戦闘・構造化データ意味を推測しない。専用の意味は、定義されたブロック境界と既知のラベル行だけから得る。
- **FR-15**: 専用ブロック同士の入れ子はMVPで禁止する。コードブロックやインデントコード内の文字列は、通常Markdownのコード内容として扱い、専用ブロックの開始・終了にはしない。
- **FR-16**: 初期語彙にないブロック名、本文用ではない予約名（`combo` 等）、未知の予約フィールドは診断付きエラーとする。通常Markdownや無害なHTMLへ黙ってフォールバックしない。

### 7.3 外部構造化データ

- **FR-17**: 敵、コンボ等の構造本質データはMarkdown本文から分離し、外部YAMLファイルを正本とする。`combo` は本文用 narrative block として認識しない。
- **FR-18**: Markdownから外部データを参照するときは、通常の相対リンクを使う。代表形は次のとおりとする。

  ```markdown
  [敵データ：璃朱人](../data/enemies/liszt.yaml)
  [コンボデータ：黙示録の雨](../data/enemies/shiro.yaml#apocalypse-rain)
  ```

- **FR-19**: MVPの敵データは `data/enemies/<enemy-id>.yaml` に置き、コンボはそのYAMLの `enemy.combos[]` に置く。敵全体の参照はfragmentなし、コンボ単体の参照は `#<combo-id>` fragment付きの通常リンクとする。`data/combos` は将来の共通combo拡張に限る。YAMLの存在確認、相対パス解決、fragmentとIDの整合、型検証、詳細項目は構造化データ契約で定める。
- **FR-20**: JSONを構造化データの手書き正本にしない。必要なJSONはYAML正本から生成する交換形式または中間表現として扱う。

### 7.4 AST変換と意味的HTML

- **FR-21**: Markdown入力はVFM/Unifiedで解析し、独自変換ツールがASTを検証・変換して意味的HTMLを生成する。
- **FR-22**: 変換後のHTMLは、見出しの階層、章・節、段落、リスト、表、リンク、画像、narrative blockの境界、専用フィールドの意味を構造として表す。
- **FR-23**: narrative blockは、後からThemeやWebPub側が識別できる安定した意味情報をHTMLに持たせる。具体的なタグ、属性、クラス、ARIA情報はHTML出力契約で固定する。
- **FR-24**: 変換ツールは、組版のための余白、書体、改ページ、装飾を意味変換の責務に混ぜない。

### 7.5 buildとpreview

- **FR-25**: buildは、Markdown、frontmatter、参照先YAMLを解析・検証・変換した中間HTMLを生成し、そのHTMLをVivliostyle CLIで組版してA5 PDFを生成する。
- **FR-26**: previewはbuildと同じ解析・検証・変換処理を通す。previewだけが別の記法解釈や寛容なフォールバックを持ってはならない。
- **FR-27**: buildとpreviewは、同じ入力・依存バージョン・Theme設定に対して、同じ意味的HTMLを参照する。
- **FR-28**: CLIの実行に必要な設定、依存関係、作業領域はリポジトリから再現できるようにする。`.vivliostyle` は設定された作業領域として使用する。

### 7.6 Themeと組版

- **FR-29**: Themeは意味的HTMLに対してA5のページ寸法、余白、書体、見出し、narrative blockの視覚表現、改ページ、ページ番号等の組版を適用する。
- **FR-30**: Themeは専用記法の解析、表示タイトルの補完、ラベルの推測、旧記法の変換を行わない。
- **FR-31**: HTMLの意味構造を変えずにThemeだけを差し替えられる境界を保つ。
- **FR-32**: A5の寸法値と組版ルールは、将来A4用の寸法・Themeを追加できるよう、変換ツールと分離した設計にする。A4用の表示調整や完成度はMVPでは保証しない。

### 7.7 旧記法の移行

- **FR-33**: 旧記法は、恒久互換ではなく一回限りの移行ツールで新しいMarkdown正本または外部YAMLへの参照へ変換する。
- **FR-34**: 移行ツールは、giftで確認できる旧ブロック名、タイトルブロック、属性リスト、星印付き判定行、旧HTMLリンク等を構造として読み取り、開始行の表示タイトル、専用ラベル行、通常のYAMLリンクへ変換する。
- **FR-35**: 旧 `combo` 本文は新しい本文ブロックへ変換しない。対応する `data/enemies/<enemy-id>.yaml` の `enemy.combos[]` に移し、Markdownには `[コンボデータ：表示名](../data/enemies/<enemy-id>.yaml#<combo-id>)` の通常リンクを置く。敵全体はfragmentなしで参照する。敵IDやコンボIDが特定できない場合は推測せず移行エラーにする。`data/combos` は将来の共通combo拡張に限る。詳細なYAMLスキーマは `docs/data-contract.md` で定める。
- **FR-36**: 移行後のMarkdownは通常のbuildで処理できることを検証する。移行ツールの実行結果をHTMLへ直接出力して正本扱いにはしない。
- **FR-37**: 移行できない構文や曖昧な入力は、入力位置、変換先候補、理由を示すエラーとして報告し、推測による内容改変をしない。

## 8. 非機能要件

### 8.1 再現性

- **NFR-01**: CLI、VFM、変換に関わる主要依存は、検証済みバージョンを固定する。
- **NFR-02**: ロックファイルを含むリポジトリから依存関係とbuild・previewの実行条件を再現できる。
- **NFR-03**: PDF生成は外部ネットワーク接続を必須条件にしない。フォントはローカルに同梱するか、事前取得済みの固定資産として扱い、オフラインで同じフォント構成を再現できるようにする。外部Webフォントだけに依存する構成は採用しない。
- **NFR-04**: Markdownから参照するYAMLの相対パスと内容を固定資産として扱い、同じ入力から同じデータを解決できるようにする。

### 8.2 品質と一貫性

- **NFR-05**: 同一のMarkdown、YAML、資産、依存バージョン、Theme設定から生成される意味的HTMLは、buildとpreviewで一貫する。
- **NFR-06**: A5 PDFは代表的なシナリオ原稿で、章タイトル、見出し、narrative block、専用フィールド、画像、リンク、改ページを確認できる品質とする。
- **NFR-07**: 変換ツールの出力契約をテスト可能にし、AST変換の結果をHTML文字列の偶然の一致だけに依存して検証しない。

### 8.3 保守性と拡張性

- **NFR-08**: Markdown解析・意味変換・構造化データ・組版・移行の責務を分離し、1つの変更が他の層の記法解釈を暗黙に変えないようにする。
- **NFR-09**: narrative blockや専用フィールドの追加は、記法仕様とHTML出力契約を更新し、必要なら構造化データ契約と検証用フィクスチャを追加してから実装する手順とする。
- **NFR-10**: A5をMVPの基準にしつつ、A4の追加でMarkdown正本、narrative block、外部YAML、意味的HTMLの変更を要求しない構造にする。

### 8.4 エラーの診断性

- **NFR-11**: エラーには、可能な限り原稿ファイル、行・列、ブロック名、フィールド名、原因、修正の方向を含める。
- **NFR-12**: build・previewはエラー時に成功扱いのPDFやHTMLを新たに公開しない。既存の生成物が残る場合も、それを今回の入力の成功結果として扱わない。
- **NFR-13**: 未知のブロック名、`combo` など本文で禁止された予約名、未知の予約フィールド、属性リスト、`.scene-title`、旧ブロック名を通常Markdownへ黙ってフォールバックしない。

## 9. 記法方針

### 9.1 正本の基本方針

- 文書の内容はMarkdownに記述する。
- frontmatterは維持し、文書ID、言語、章に必要なメタデータを担う。表示本文の代替にはしない。
- frontmatter直後の最初の通常H1を章タイトルとする。H1には `.scene-title` などの属性を付けない。
- narrative blockは `:::種別 表示タイトル` で開始し、列1の単独 `:::` で終了する。表示タイトルは必須で、属性リストは使わない。
- 本文用の専用名は7種類だけとし、名称の追加は記法仕様とHTML出力契約の更新を伴う。
- 敵・コンボ等の本質データは外部YAMLに置き、Markdownでは人間が読める通常リンクで参照する。

### 9.2 角括弧ラベルと本文

- 角括弧ラベルは、専用ブロック直下の列1にある既知ラベルだけをASTで解釈する。本文全体の正規表現置換は行わない。
- `check` では開始フェンス後の空行を除く先頭から連続するフィールド前置部に `[技能] 値` と `[難易度] 0以上の整数` をちょうど1組置き、任意の単独 `[必須]` をその組に付ける。通常Markdown本文開始後の機械フィールドや2組目は許可しない。
- `info` 等では既知ラベルと値を人間可読フィールドとして保持する。`[技能]` と `[難易度]` のペアも複数許容し、旧原稿の複数項目を1つに潰さない。
- 太字、引用、通常のリスト、リンク、画像、表から専用の意味を推測しない。未知の予約フィールドはエラーとして診断する。
- 専用ブロックの入れ子はMVPで禁止する。

### 9.3 外部構造化データ

- 敵、コンボ等の構造化データはYAMLファイルを正本とする。JSONを手書き正本にしない。
- Markdownの参照は通常リンクで記述する。敵全体は `[敵データ：名前](../data/enemies/<enemy-id>.yaml)`、コンボ単体は `[コンボデータ：表示名](../data/enemies/<enemy-id>.yaml#<combo-id>)` とする。`data/combos` は将来の共通combo拡張用であり、MVPのコンボ置き場ではない。
- リンク表示、相対パスの解決、YAMLの詳細スキーマ、敵・コンボ間の参照制約は `docs/data-contract.md` で具体化する。
- `:::combo`、`:::enemy` のような本文ブロックは新しい正本では受理しない。

### 9.4 旧記法

- `serif`、`rp`、`select`、旧 `check` 等の旧名は、新規原稿の正本名にしない。
- 属性リスト、`.scene-title`、`section-title` 等の旧構文は移行ツールだけが入力として扱い、通常のbuild・previewはエラーにする。
- 旧記法から移行した結果は、通常のMarkdownと外部YAMLへの通常リンクとしてレビューできなければならない。

## 10. 生成物の管理

| 種別 | 位置付け | 扱い |
| --- | --- | --- |
| Markdown | 本文の唯一の正本 | 編集・レビューの対象。内容変更はMarkdownに対して行う。 |
| YAML | 敵・コンボ等の構造化データの正本 | Markdownから相対リンクで参照する。詳細契約に従って検証する。 |
| 中間HTML | 変換結果 | buildで生成する。手編集せず、MarkdownとYAMLから再生成する。MVPの納品物に含める。 |
| PDF | 組版結果 | buildで生成する。配布・目視確認の対象。MarkdownやHTMLの代わりに編集しない。 |
| `.vivliostyle` | CLIの作業領域 | キャッシュ・一時状態として扱い、正本や納品物に含めない。再生成可能な状態にする。 |
| 画像・フォント等の資産 | MarkdownまたはYAMLから参照される入力 | ライセンスと配置を管理し、PDF生成に必要な資産をオフラインで解決できるようにする。 |

生成物の具体的な出力パスやファイル命名はbuild仕様で定めるが、正本と生成物の責務分離は変更しない。生成物をリポジトリに置く場合も、手編集せず、再生成可能な成果物として扱う。

MVPの出力対象はPDFと中間HTMLである。WebPubは次段階の設計対象とし、EPUBは対象外とする。

## 11. エラー方針

### 11.1 必ずエラーにする事象

- frontmatterの開始・終了、YAML mapping、必須 `id`、値の型が不正である。
- frontmatter直後の最初の通常H1がない、H1が空である、H1が複数ある、またはH1に `.scene-title` 等の属性を付けている。
- 開始行に表示タイトルがない、開始行に属性リストがある、名前とタイトルの区切りや文字種が不正である。
- 初期語彙にない専用ブロック名、本文用ではない `combo`・`enemy` 等の予約名がある。
- 専用ブロックの終了記号 `:::` がない、列1以外の終了記号、ブロック外の余分な `:::`、終了位置の不整合がある。
- 専用ブロック同士のMVP禁止の入れ子がある。
- 専用ブロック内の列1で、既知の形式に見える未知の予約フィールドがある。
- `check` の機械可読前置部が開始フェンス後の空行を除く先頭から連続していない、技能値が空、難易度が0以上の整数でない、技能/難易度ペアが未完、2組目がある、通常Markdown本文開始後に機械フィールドがある、または `[必須]` の位置や形式が不正である。
- `info` 等の技能/難易度ペアが未完である、既知ラベルの値が空である、同一ラベルの許容回数に違反する。
- 本文が空、または本文を標準Markdownとして解釈できない。
- 旧ブロック名、属性リスト、`.scene-title` を通常のbuild・previewで受理しようとする。
- YAML参照リンクの形式、相対パス、存在確認、スキーマ検証に違反する。ただし各検証の詳細は構造化データ契約で定める。
- ASTから意味的HTMLへ変換できない構造がある。

### 11.2 共通の振る舞い

- buildとpreviewは、上記事象を警告だけで通過させない。
- エラー時は非成功の終了結果を返し、原因となった原稿位置を示す。
- エラー時に旧記法を推測して補完したり、未認識の専用記法を通常HTMLへフォールバックしたりしない。
- previewもbuildと同じエラーを表示し、エラーを隠したプレビューを提供しない。
- 移行ツールは通常の変換エラーと区別して、変換元位置・変換先候補・失敗理由を示す。

## 12. 受け入れ条件

### 12.1 A5 MVPの完了条件

1. frontmatterを維持したMarkdownから、frontmatter直後の最初の通常H1を章タイトルとしてASTと意味的HTMLへ反映できる。
2. 開始行が `:::dialogue 渚` のような表示タイトル付きで記述され、単独 `:::` で閉じられる。
3. `dialogue`、`roleplay`、`choice`、`check`、`info`、`e-lois`、`battle` の7種類を検証・変換できる。
4. `check` が開始フェンス後の空行を除く先頭から連続するフィールド前置部から、ちょうど1組の技能/難易度と任意の `[必須]` を保持できる。本文開始後の機械フィールドと2組目はエラーになる。
5. `info` 等の既知の角括弧ラベルが専用ブロック直下のASTから人間可読フィールドとして保持され、複数の技能/難易度ペアが欠落なく出力される。
6. `choice` がリストなしの自然文、リスト、表などを受理し、選択対象や分岐の記述を作者に強制しない。
7. 敵・コンボの構造化データが `data/enemies/<enemy-id>.yaml` の `enemy.combos[]` にあり、Markdownが敵全体をfragmentなし、コンボ単体を `[コンボデータ：表示名](../data/enemies/<enemy-id>.yaml#<combo-id>)` の通常リンクで参照できる。`combo` 本文ブロックは受理しない。
8. 属性リスト、`.scene-title`、太字・引用からの意味推測、未知ブロック、未知の予約フィールド、閉じ忘れ、入れ子が、位置を含むエラーになる。
9. 変換後のHTMLをVivliostyle CLIでA5 PDFに組版でき、PDFと中間HTMLがMVPの成果物として得られる。
10. Themeは組版を担当し、専用記法の解釈や正規表現によるHTML後処理を担当していない。
11. buildとpreviewが同じ変換処理を使用し、どちらか一方だけが旧記法や不完全な入力を許容しない。
12. CLIとVFMの検証済みバージョンが固定され、依存関係ロックと `.vivliostyle` の作業領域設定がリポジトリから再現できる。
13. ネットワークに接続できない環境でも、固定したフォント資産で同じフォント構成のPDFを生成できる。
14. 対象範囲として定めた旧記法を移行ツールで新しいMarkdownと外部YAML参照へ変換でき、変換後の原稿を通常のbuildで処理できる。
15. 代表的な原稿でA5のページ寸法、章タイトル、見出し、narrative block、フィールド、画像、リンク、改ページを目視確認し、重大な欠落や崩れがない。

### 12.2 将来A4の扱い

- A4は、MVP完了後に同じMarkdown、外部YAML、意味的HTMLを使って追加する。
- A4追加時は、ページ寸法、余白、文字サイズ、改ページ、narrative blockの収まりをA4向けThemeまたは設定として調整する。
- A4を追加可能な責務分離はMVPで確認するが、A4のPDF出力、視覚品質、受け入れ試験はMVP完了条件に含めない。

## 13. 段階計画

### 第1段階: 契約の確定

- 本書を基に、本文用ブロックの正確な文法、表示タイトル、ラベル行、`check` の機械可読項目を記した記法仕様書を作成する。
- 意味的HTMLのタグ、属性、クラス、見出し・章構造を記したHTML出力契約を作成する。
- 敵・コンボ等のYAML詳細スキーマを `docs/data-contract.md` として作成する。
- 各ブロック、`info`・`e-lois` の複数ペア、正常系、エラー系、外部YAML参照、旧記法移行用のフィクスチャを定義する。

### 第2段階: MVP変換基盤

- VFM/Unifiedの検証済みバージョンを固定する。
- ASTでfrontmatter、章タイトル、本文用ブロック、既知ラベルを認識・検証し、意味的HTMLへ変換する独自変換ツールを実装する。
- unknown、予約フィールド、開始行不正、閉じ忘れ、ペア不整合、入れ子を検出する。
- 外部YAMLの相対リンクを構造化データ契約に沿って検証する。

### 第3段階: A5組版と実行経路

- Themeを意味的HTMLの組版専用として整理する。
- `.vivliostyle` をworkspaceDirに設定し、ロック済みCLIでbuild・previewを接続する。
- オフラインで再現できるフォント構成を組み込む。
- 中間HTMLとA5 PDFを生成し、代表原稿で視覚確認する。

### 第4段階: 移行と受け入れ

- gift由来の対象旧記法を一回限りの移行ツールで新正本へ変換する。
- `combo` と敵の構造データを外部YAMLへ移し、Markdownの通常リンクを生成する。
- 移行後のMarkdownをレビューし、通常のbuildで再生成する。
- 受け入れ条件を満たす自動検証と目視確認を実行する。

### MVP後

- 構造化データ契約と意味的HTMLを再利用するWebPub出力を設計・実装する。
- 同じ変換契約を維持したままA4用のTheme・設定を追加する。
- 変換APIが安定した時点で、単一リポジトリから再利用パッケージを分離するか判断する。

## 14. 保留事項

以下はMVPの方針を変えず、次の仕様書またはMVP後の設計で具体化する事項である。

- frontmatterの必須キー、章IDの命名規則、複数章を束ねる設定の形式
- 本文用7種類それぞれの正確な開始・終了記号、表示タイトルの空白処理、本文の許可構造
- 専用ブロック直下の既知ラベル一覧、ラベルの多重度、ASTフィールドの詳細型
- `info`・`e-lois` の複数技能/難易度ペアをHTMLへ表現する具体的な出力契約
- 専用ブロックを表現するHTML要素、安定したクラス・data属性・ARIA属性の最終セット
- 敵・コンボのYAMLスキーマ、ファイル配置、参照整合性、JSON交換形式の生成規則（`docs/data-contract.md`）
- giftの `section-title`、`trailer`、`toc`、説明リスト等を新正本へ移行する際の個別変換規則
- 採用するフォントファイル、ライセンス表記、フォールバック順、配布方法
- A5の細かな改ページ規則、目次やページ番号のHTML出力契約との接続
- WebPubが利用するメタデータとナビゲーションの契約
- A4の寸法・余白・文字組み・Theme調整
- API安定後のパッケージ分離単位と公開方法

保留事項は、MVPで採用するA5、frontmatter、通常のH1、7種類の本文用ブロック、AST変換、外部YAML、build/preview共通経路、旧記法の一回限り移行、PDFと中間HTMLの成果物という決定を変更しない。
