# TRPGシナリオ組版環境 要件定義書

## 1. 文書の位置付け

- 状態: 初稿
- 対象: TRPGシナリオをMarkdownで執筆し、意味的HTMLを経由してVivliostyleでPDF化する再利用可能な環境
- MVPの判型: A5
- 正本: シナリオのMarkdown
- 生成物: 中間HTML、PDF、`.vivliostyle` 作業領域

本書で決定したMVPの方針は、後続の記法仕様書・HTML出力契約・実装設計の前提とする。後続仕様で具体化する項目を保留事項として挙げる場合も、MVPの対象範囲や方針を未決定に戻すものではない。

## 2. 目的

シナリオ作者がMarkdownだけを編集して、TRPGの進行に必要な会話、ロールプレイ指示、判定、情報、戦闘などを読みやすく組版したPDFを再現可能に生成できるようにする。

次の性質を同時に満たすことを目的とする。

1. Markdownを唯一の正本とし、HTMLやPDFを手作業で維持しない。
2. シナリオ固有の記法を、正規表現による後処理ではなくVFM/UnifiedのAST上で検証・変換する。
3. 変換結果を意味的HTMLとして保持し、A5の組版はThemeに分離する。
4. buildとpreviewで同じ変換・検証結果を得る。
5. 不正な記法を黙って通さず、執筆時点で修正できるエラーとして報告する。

## 3. スコープ

### 3.1 MVPに含めるもの

- 単一リポジトリ内で完結するMarkdown執筆環境
- frontmatterと通常のH1による章タイトル
- VFM/Unifiedを基盤にしたASTベースの独自変換
- 専用ブロックの初期語彙
  `dialogue`, `roleplay`, `choice`, `check`, `info`, `e-lois`, `battle`, `combo`
- 専用ブロックを含むMarkdownから意味的HTMLを生成する変換ツール
- 変換ツールを利用したVivliostyle CLIのbuildとpreview
- A5 PDFの安定した生成
- PDF生成に用いた中間HTMLの出力
- 専用ブロックの未知名、閉じ忘れ、必須属性不足、MVPで禁止する入れ子の検証
- CLI/VFMの検証済みバージョン固定と依存関係ロック
- Vivliostyleの `workspaceDir` として `.vivliostyle` を使用する構成
- 旧記法を正本へ一度だけ変換する移行ツール
- オフラインでフォントを再現できる構成

### 3.2 MVPに含めないもの

- WebPub出力。これはMVP後の次段階で扱う。
- EPUB出力。現行計画の対象外とする。
- A4 PDFの対応およびA4向けの完成度保証。将来追加できる設計にはするが、MVPの完了条件には含めない。
- 旧記法をbuildまたはpreviewで恒久的に受け付ける互換層
- Markdown以外を正本とする編集フロー
- ThemeがMarkdownの記法を解釈する仕組み
- MVP時点でのパッケージ分離。APIが安定した後に分離を検討する。

## 4. 用語

| 用語 | 定義 |
| --- | --- |
| Markdown正本 | 作者が編集・レビューする唯一のシナリオ原稿。frontmatter、通常のMarkdown、専用ブロックを含む。 |
| VFM | Vivliostyle Flavored Markdown。現在のMarkdown入力を解析する基盤。 |
| Unified | MarkdownをASTとして扱う変換基盤。専用ブロックの認識・検証・変換はこのASTの段階で行う。 |
| AST | Markdownの構造を表す抽象構文木。文字列の正規表現置換で代用しない。 |
| 専用ブロック | シナリオ固有の意味を持つ、名前と内容を備えたMarkdown記法。 |
| 意味的HTML | 見た目だけでなく、見出し、節、段落、リスト、表、リンク、画像、専用ブロックの意味が構造として表現されたHTML。 |
| Theme | 意味的HTMLに対してページ寸法、書体、余白、改ページ、装飾などの組版を適用するCSS等の資産。 |
| CLI | Vivliostyleを実行してHTMLを組版し、PDFまたはプレビューを提供するコマンドライン実行部。 |
| build | Markdownを変換・検証し、中間HTMLとPDFを生成する処理。 |
| preview | buildと同じMarkdown変換・検証結果を閲覧する処理。 |
| 旧記法 | giftで使われている正規表現後処理を前提とした記法など、新しい正本では採用しない記法。 |
| 移行ツール | 旧記法を一度だけ正本のMarkdownへ変換する補助ツール。通常のbuild経路には含めない。 |

## 5. 参照元と確認できた事実

視覚・機能の参照元は、リポジトリ内の `gift` プロジェクトに限定する。確認できた事実は次のとおりであり、これを超える機能は本書の根拠にしない。

- [`gift/package.json`](../gift/package.json) には `build` と `preview` のスクリプトがあり、`@vivliostyle/cli` を依存関係としている。
- [`gift/vivliostyle.config.js`](../gift/vivliostyle.config.js) は判型をA5に設定し、Theme、複数のHTMLエントリ、`manuscripts` のエントリコンテキストを指定している。
- `gift/manuscripts` にはMarkdownと生成HTMLの対応ファイルが存在する。Markdownにはfrontmatter、通常のH1、`:::section-title`、会話・ロールプレイ・判定・情報・Eロイス・戦闘・コンボ等の記法が確認できる。
- [`gift/_postReplaceList.json`](../gift/_postReplaceList.json) は `serif`、`rp`、`select`、`check`、`info`、`e-lois`、`battle`、`combo` などの文字列を正規表現でHTMLへ置換している。また、`section-title`、`trailer`、`toc`、説明リスト、改ページ、リンク等の置換も定義している。
- [`gift/manuscripts/md4.md`](../gift/manuscripts/md4.md) と [`gift/manuscripts/md4.html`](../gift/manuscripts/md4.html) では、専用記法がHTMLの専用クラス付き要素に変換され、通常の見出しがHTMLのsectionと見出し要素として出力されている。
- [`gift/themes/vivliostyle-theme-dx3rd-ammonite/main.css`](../gift/themes/vivliostyle-theme-dx3rd-ammonite/main.css) はA5のページ寸法、見出し、専用クラス、改ページ、リンクのページ番号表示などを定義している。また、Google Fontsを外部URLから読み込んでいる。

以上を参照しつつ、新環境では正規表現後処理を廃止し、章タイトル、専用ブロック、フォント再現性を新しい要件として再設計する。

## 6. アーキテクチャ

### 6.1 処理の流れ

```text
Markdown + frontmatter + 画像等の資産
        │
        ▼
VFM/Unifiedによる解析
        │
        ▼
ASTの検証・専用ノードの意味変換
        │
        ▼
意味的HTML（中間生成物）
        │
        ├── Vivliostyle CLI + Theme ──> A5 PDF
        └── preview ───────────────────> 同じ変換結果の閲覧
```

### 6.2 責務の分離

- **Markdown** は内容と文書構造を表す。作者が編集する唯一の正本である。
- **VFM/Unifiedと独自変換ツール** は、Markdownを解析し、専用ブロックを検証し、意味的HTMLへ変換する。専用記法の認識に正規表現によるHTML後処理を使用しない。
- **意味的HTML** は、通常のMarkdown構造と専用ブロックの意味を保持する中間契約である。将来のWebPubなど、PDF以外の出力の基盤にもできる構造とする。
- **Theme** は意味的HTMLの組版だけを担当する。Markdownの記法、旧記法、属性の補完、意味の判断を担当しない。
- **Vivliostyle CLI** は、変換済みHTMLをA5に組版し、PDFとpreviewを提供する。
- **移行ツール** は、旧記法の入力を新しいMarkdown正本へ変換する。通常の変換パイプラインとは別の一回限りの処理とする。

### 6.3 バージョンと作業領域

- CLIとVFMは、実際にbuild・preview・PDF出力を検証したバージョンを明示的に固定する。
- 依存関係のロックファイルをリポジトリで管理し、未検証の `latest` 追随を実行時の前提にしない。
- Vivliostyleの `workspaceDir` は `.vivliostyle` に固定する。キャッシュ、一時ファイル、CLIが生成する作業状態はここに集約し、Markdown正本と混在させない。
- MVPは単一リポジトリで完成させる。変換APIとHTML出力契約が安定した後に、再利用単位を見極めてパッケージ分離を検討する。

## 7. 機能要件

### 7.1 原稿管理と章構造

- **FR-01**: シナリオ本文、専用ブロック、章メタデータはMarkdownに記述する。
- **FR-02**: 章の機械可読な識別子や文書メタデータはfrontmatterに置く。印刷上の章タイトルは専用のタイトルブロックではなく、通常のMarkdownのH1で表す。
- **FR-03**: 章原稿は、必要なfrontmatterと通常のH1を持つ構造を標準とする。H1の表示文字列は生成HTMLの章タイトルに反映する。
- **FR-04**: 通常のMarkdownの段落、見出し、リスト、表、リンク、画像等を、内容を失わずにHTMLへ変換する。
- **FR-05**: 画像など原稿が参照する資産は、Markdownからの相対参照を維持できるようにする。生成HTMLやPDFを直接編集して参照を補正する運用は採用しない。

### 7.2 専用ブロック

- **FR-06**: MVPの正本で認識する専用ブロック名は、次の8種類に限定する。

  | ブロック | 用途 |
  | --- | --- |
  | `dialogue` | 登場人物等の台詞・会話を表す。 |
  | `roleplay` | プレイヤーが自由に演技する場面や進行指示を表す。 |
  | `choice` | 選択肢、分岐、選択に応じた進行を表す。 |
  | `check` | 判定、技能、難易度、判定結果等を表す。 |
  | `info` | GM向けの情報、補足、参照情報等を表す。 |
  | `e-lois` | Eロイスに関するデータや処理を表す。 |
  | `battle` | 戦闘の敵、配置、終了条件等を表す。 |
  | `combo` | コンボの構成、条件、効果等を表す。 |

- **FR-07**: 専用ブロックは、VFM/UnifiedのAST上で名前、属性、本文、開始位置、終了位置を保持して扱う。単なる文字列検索でHTML断片を組み立てない。
- **FR-08**: 各ブロックの必須属性、属性値の形式、見出しの扱い、本文として許可するMarkdownは記法仕様書で定義し、変換時に検証する。
- **FR-09**: 必須属性が不足している専用ブロックは、build・previewともにエラーとする。
- **FR-10**: MVPでは専用ブロック同士の入れ子を禁止する。入れ子を検出した場合はエラーとする。通常のMarkdown本文を専用ブロック内に置ける範囲は、記法仕様書とHTML出力契約で定義する。
- **FR-11**: 初期語彙にない専用ブロック名は未知の専用記法としてエラーとする。未知名を一般のHTMLや無害なテキストとして黙って通さない。
- **FR-12**: `dialogue`、`roleplay`、`choice` 等の正本名は新規原稿で使用する。giftで確認できる `serif`、`rp`、`select` 等は旧記法として移行ツールでのみ扱い、build・previewの恒久互換名にはしない。

### 7.3 AST変換と意味的HTML

- **FR-13**: Markdown入力はVFM/Unifiedで解析し、独自変換ツールがASTを検証・変換して意味的HTMLを生成する。
- **FR-14**: 変換後のHTMLは、見出しの階層、章・節、段落、リスト、表、リンク、画像、専用ブロックの境界を構造として表す。
- **FR-15**: 専用ブロックは、後からThemeやWebPub側が識別できる安定した意味情報をHTMLに持たせる。具体的なタグ、属性、クラス、ARIA情報はHTML出力契約で固定する。
- **FR-16**: 変換ツールは、組版のための余白、書体、改ページ、装飾を意味変換の責務に混ぜない。

### 7.4 buildとpreview

- **FR-17**: buildは、Markdownを解析・検証・変換した中間HTMLを生成し、そのHTMLをVivliostyle CLIで組版してA5 PDFを生成する。
- **FR-18**: previewはbuildと同じ解析・検証・変換処理を通す。previewだけが別の記法解釈や寛容なフォールバックを持ってはならない。
- **FR-19**: buildとpreviewは、同じ入力・依存バージョン・Theme設定に対して、同じ意味的HTMLを参照する。
- **FR-20**: CLIの実行に必要な設定、依存関係、作業領域はリポジトリから再現できるようにする。`.vivliostyle` は設定された作業領域として使用する。

### 7.5 Themeと組版

- **FR-21**: Themeは意味的HTMLに対してA5のページ寸法、余白、書体、見出し、専用ブロックの視覚表現、改ページ、ページ番号等の組版を適用する。
- **FR-22**: Themeは専用記法の解析、属性不足の補完、旧記法の変換を行わない。
- **FR-23**: HTMLの意味構造を変えずにThemeだけを差し替えられる境界を保つ。
- **FR-24**: A5の寸法値と組版ルールは、将来A4用の寸法・Themeを追加できるよう、変換ツールと分離した設計にする。A4用の表示調整や完成度はMVPでは保証しない。

### 7.6 旧記法の移行

- **FR-25**: 旧記法は、恒久互換ではなく一回限りの移行ツールで新しいMarkdown正本へ変換する。
- **FR-26**: 移行ツールは、giftで確認できるタイトルブロックや旧ブロック名など、対象として定めた旧記法を構造として読み取り、frontmatter・通常のH1・新しい専用ブロックへ変換する。
- **FR-27**: 移行後のMarkdownは通常のbuildで処理できることを検証する。移行ツールの実行結果をHTMLへ直接出力して正本扱いにはしない。
- **FR-28**: 移行できない構文や曖昧な入力は、入力位置と理由を示すエラーとして報告し、推測による内容改変をしない。

## 8. 非機能要件

### 8.1 再現性

- **NFR-01**: CLI、VFM、変換に関わる主要依存は、検証済みバージョンを固定する。
- **NFR-02**: ロックファイルを含むリポジトリから依存関係とbuild・previewの実行条件を再現できる。
- **NFR-03**: PDF生成は外部ネットワーク接続を必須条件にしない。フォントはローカルに同梱するか、事前取得済みの固定資産として扱い、オフラインで同じフォント構成を再現できるようにする。外部Webフォントだけに依存する構成は採用しない。

### 8.2 品質と一貫性

- **NFR-04**: 同一のMarkdown、資産、依存バージョン、Theme設定から生成される意味的HTMLは、buildとpreviewで一貫する。
- **NFR-05**: A5 PDFは代表的なシナリオ原稿で、章タイトル、見出し、専用ブロック、画像、リンク、改ページを確認できる品質とする。
- **NFR-06**: 変換ツールの出力契約をテスト可能にし、AST変換の結果をHTML文字列の偶然の一致だけに依存して検証しない。

### 8.3 保守性と拡張性

- **NFR-07**: Markdown解析・意味変換・組版・移行の責務を分離し、1つの変更が他の層の記法解釈を暗黙に変えないようにする。
- **NFR-08**: 専用ブロックの追加は、記法仕様とHTML出力契約を更新し、検証用フィクスチャを追加してから実装する手順とする。
- **NFR-09**: A5をMVPの基準にしつつ、A4の追加でMarkdown正本や意味的HTMLの変更を要求しない構造にする。

### 8.4 エラーの診断性

- **NFR-10**: エラーには、可能な限り原稿ファイル、行・列、専用ブロック名、原因、修正の方向を含める。
- **NFR-11**: build・previewはエラー時に成功扱いのPDFやHTMLを新たに公開しない。既存の生成物が残る場合も、それを今回の入力の成功結果として扱わない。

## 9. 記法方針

### 9.1 正本の基本方針

- 文書の内容はMarkdownに記述する。
- frontmatterは文書ID、言語、章に必要なメタデータを担い、表示本文の代替にはしない。
- 章の表示タイトルは通常のH1にする。既存の `section-title` のような専用タイトルブロックを新しい正本の必須構文にしない。
- 専用ブロックは、専用名、必要な属性、本文、明示的な終端を持つ構造として解析する。
- 正本で使える専用名はMVPの8語だけとし、名称の追加は仕様更新を伴う。

### 9.2 属性と本文

- 必須属性と許容される属性は、ブロック種別ごとのスキーマとして定義する。
- 属性が不足、形式不正、またはブロックの構造に適合しない場合はbuild・previewを失敗させる。
- 専用ブロック内の本文は、HTMLへ変換可能な標準Markdownの範囲を仕様書で定める。
- 専用ブロックの入れ子はMVPで禁止する。
- 記法を正規表現でHTMLへ置換する実装、未認識の構文をHTML断片として通す実装は採用しない。

### 9.3 旧記法

- `serif`、`rp`、`select` などgiftの現行原稿で確認できる旧名は、新規原稿の正本名にしない。
- 旧記法の変換は移行ツールの責務とし、通常のbuild・previewに旧名の互換分岐を追加しない。
- 旧記法から移行した結果は、通常のMarkdownとしてレビュー可能でなければならない。

## 10. 生成物の管理

| 種別 | 位置付け | 扱い |
| --- | --- | --- |
| Markdown | 唯一の正本 | 編集・レビューの対象。内容変更はMarkdownに対して行う。 |
| 中間HTML | 変換結果 | buildで生成する。手編集せず、Markdownから再生成する。MVPの納品物に含める。 |
| PDF | 組版結果 | buildで生成する。配布・目視確認の対象。MarkdownやHTMLの代わりに編集しない。MVPの納品物に含める。 |
| `.vivliostyle` | CLIの作業領域 | キャッシュ・一時状態として扱い、正本や納品物に含めない。再生成可能な状態にする。 |
| 画像・フォント等の資産 | Markdownから参照される入力 | ライセンスと配置を管理し、PDF生成に必要な資産をオフラインで解決できるようにする。 |

生成物の具体的な出力パスやファイル命名はbuild仕様で定めるが、正本と生成物の責務分離は変更しない。生成物をリポジトリに置く場合も、手編集せず、再生成可能な成果物として扱う。

MVPの出力対象はPDFと中間HTMLである。WebPubは次段階の設計対象とし、EPUBは対象外とする。

## 11. エラー方針

### 11.1 必ずエラーにする事象

- 初期語彙にない専用ブロック名
- 専用ブロックの閉じ忘れ、終端の不整合
- 専用ブロックの必須属性不足、属性形式不正
- 専用ブロックのMVP禁止の入れ子
- frontmatterの構文不正、または章に必要なメタデータの欠落
- 章タイトルとして必要な通常のH1がない、または章構造に反する入力
- ASTから意味的HTMLへ変換できない構造

### 11.2 共通の振る舞い

- buildとpreviewは、上記事象を警告だけで通過させない。
- エラー時は非成功の終了結果を返し、原因となった原稿位置を示す。
- エラー時に旧記法を推測して補完したり、未認識の専用記法を通常HTMLへフォールバックしたりしない。
- previewもbuildと同じエラーを表示し、エラーを隠したプレビューを提供しない。
- 移行ツールは通常の変換エラーと区別して、変換元位置・変換先候補・失敗理由を示す。

## 12. 受け入れ条件

### 12.1 A5 MVPの完了条件

1. 正本のMarkdownから、VFM/UnifiedのASTを経由して意味的HTMLを生成できる。
2. 同じMarkdownをbuildとpreviewに渡したとき、専用ブロックの解釈と意味的HTMLが一致する。
3. `dialogue`、`roleplay`、`choice`、`check`、`info`、`e-lois`、`battle`、`combo` の8種類を検証・変換できる。
4. 未知の専用記法、閉じ忘れ、必須属性不足、専用ブロックの入れ子が、位置を含むエラーになる。
5. 章タイトルがfrontmatterと通常のH1で表現され、旧タイトルブロックに依存せずに意味的HTMLとPDFへ反映される。
6. 変換後のHTMLをVivliostyle CLIでA5 PDFに組版できる。PDFと中間HTMLがMVPの成果物として得られる。
7. Themeは組版を担当し、専用記法の解釈や正規表現によるHTML後処理を担当していない。
8. buildとpreviewが同じ変換処理を使用し、どちらか一方だけが旧記法や不完全な入力を許容しない。
9. CLIとVFMの検証済みバージョンが固定され、依存関係ロックと `.vivliostyle` の作業領域設定がリポジトリから再現できる。
10. ネットワークに接続できない環境でも、固定したフォント資産で同じフォント構成のPDFを生成できる。
11. 対象範囲として定めた旧記法を移行ツールで新しいMarkdownへ変換でき、変換後の原稿を通常のbuildで処理できる。
12. 代表的な原稿でA5のページ寸法、章タイトル、見出し、専用ブロック、画像、リンク、改ページを目視確認し、重大な欠落や崩れがない。

### 12.2 将来A4の扱い

- A4は、MVP完了後に同じMarkdownと意味的HTMLを使って追加する。
- A4追加時は、ページ寸法、余白、文字サイズ、改ページ、専用ブロックの収まりをA4向けThemeまたは設定として調整する。
- A4を追加可能な責務分離はMVPで確認するが、A4のPDF出力、視覚品質、受け入れ試験はMVP完了条件に含めない。

## 13. 段階計画

### 第1段階: 契約の確定

- 本書を基に、専用ブロックの正確な文法・属性スキーマを記した記法仕様書を作成する。
- 意味的HTMLのタグ、属性、クラス、見出し・章構造を記したHTML出力契約を作成する。
- 8種類のブロック、正常系、エラー系、旧記法移行用のフィクスチャを定義する。

### 第2段階: MVP変換基盤

- VFM/Unifiedの検証済みバージョンを固定する。
- ASTで専用ブロックを認識し、検証し、意味的HTMLへ変換する独自変換ツールを実装する。
- unknown、閉じ忘れ、必須属性不足、入れ子を検出する。
- frontmatterと通常のH1を章構造として扱う。

### 第3段階: A5組版と実行経路

- Themeを意味的HTMLの組版専用として整理する。
- `.vivliostyle` をworkspaceDirに設定し、ロック済みCLIでbuild・previewを接続する。
- オフラインで再現できるフォント構成を組み込む。
- 中間HTMLとA5 PDFを生成し、代表原稿で視覚確認する。

### 第4段階: 移行と受け入れ

- gift由来の対象旧記法を一回限りの移行ツールで新正本へ変換する。
- 移行後のMarkdownをレビューし、通常のbuildで再生成する。
- 受け入れ条件を満たす自動検証と目視確認を実行する。

### MVP後

- 意味的HTMLを再利用するWebPub出力を設計・実装する。
- 同じ変換契約を維持したままA4用のTheme・設定を追加する。
- 変換APIが安定した時点で、単一リポジトリから再利用パッケージを分離するか判断する。

## 14. 保留事項

以下はMVPの方針を変えず、次の仕様書またはMVP後の設計で具体化する事項である。

- 8種類それぞれの正確な開始・終了記号、必須属性名、属性値の型、本文の許可構造
- 専用ブロックを表現するHTML要素、安定したクラス・data属性・ARIA属性の最終セット
- frontmatterの必須キー、章IDの命名規則、複数章を束ねる設定の形式
- giftの `section-title`、`trailer`、`toc`、説明リスト等を新正本へ移行する際の個別変換規則
- 採用するフォントファイル、ライセンス表記、フォールバック順、配布方法
- A5の細かな改ページ規則、目次やページ番号のHTML出力契約との接続
- WebPubが利用するメタデータとナビゲーションの契約
- A4の寸法・余白・文字組み・Theme調整
- API安定後のパッケージ分離単位と公開方法

保留事項は、MVPで採用するA5、Markdown正本、AST変換、8語彙、build/preview共通経路、旧記法の一回限り移行、PDFと中間HTMLの成果物という決定を変更しない。
